# ADR-002 (Task2). Схема топиков Kafka с партиционированием по регионам

## Общая информация

1. **Родительский артефакт** - `ADR-001-domain-events.md` (модель и каталог событий).
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.

## Контекст

Платформа работает в нескольких географических регионах (Юго-Восточная Азия, Южная Америка и др.).
Данные резидентов должны храниться в их регионе (data residency), а нагрузка одного региона
не должна влиять на другой ("шумный сосед"). Поэтому нужно определить схему топиков и способ
партиционирования с учётом регионов.

Kafka даёт порядок сообщений только **внутри партиции**, поэтому ключ партиции определяет,
какие события упорядочены относительно друг друга.

## Требования

| No. | Требование |
|---|---|
| 1 | События разделены по регионам (изоляция и data residency). |
| 2 | Порядок событий сохраняется для одной сущности (поездка, водитель, платёж). |
| 3 | Высокочастотные потоки (позиции водителей) не вытесняют и не тормозят денежные события. |
| 4 | Пропускная способность шины >= 1 млн сообщений/с суммарно. |
| 5 | Схемы событий версионируются и проверяются. |

## Решение

### Схема имени топика

```
<jurisdiction>.<domain>.<event-type>.v<version>
```

Примеры:
- `ru.booking.booking-created.v1`
- `id.driver.driver-location-updated.v1`
- `br.payments.payment-captured.v1`

Соответствие с конвертом события: `event-type` в имени топика - **kebab-case**, а `eventType`
в конверте - **PascalCase**; правило преобразования: `booking-created` <-> `BookingCreated`.
Версии согласованы: `.v1` в имени топика и `version: 1` в конверте.

Пространство имён топиков - **на юрисдикцию (страну)**: здесь `<jurisdiction>` = юрисдикция
(`ru`, `id`, `br`, `sg`), а не отдельный регион развёртывания. Физически в каждой юрисдикции
есть кластеры Kafka в обоих её регионах развёртывания. Так как запись в юрисдикции идёт на
primary-регион (см. Task3/ADR-001), бизнес-топики **зеркалируются односторонне: primary ->
standby** (MirrorMaker 2), а при failover направление зеркала меняется вместе со сменой ролей.
Одностороннее направление и есть защита от петель; имена топиков сохраняются
(`IdentityReplicationPolicy`), смещения транслируются checkpoint-коннектором. Между
юрисдикциями зеркалируются только справочные и обезличенные агрегатные топики (см.
Task3/ADR-002). Внутри топика порядок гарантирован в рамках сущности (ключ партиции), а не
глобально.

### Партиционирование

| Класс топика | Ключ партиции | Число партиций (на юрисдикцию) | Обоснование |
|---|---|---|---|
| Поездки/брони (`Booking*`, `Ride*`) | `rideId` | 24 | порядок по поездке, средняя частота |
| Деньги (`Payment*`, `Payout*`) | `paymentId` / `payoutId` | 12 | порядок по операции, аудит |
| Геопозиции (`DriverLocationUpdated`) | `driverId` | 48 | самый высокий поток, нужен параллелизм |
| Цены/зоны (`PriceUpdated`, `ZoneEntered`) | `region + zoneId` | 24 | агрегирование по зоне |
| ETA (`EtaUpdated`) | `rideId` | 24 | частые обновления по активным поездкам |
| Диспетчеризация/офферы (`DriverOffer*`) | `driverId` | 24 | порядок офферов по водителю |
| Баланс зон (`ZoneBalanceUpdated`, `ZoneDeficitDetected`, `DemandForecastUpdated`) | `region + zoneId` | 24 | агрегирование по зоне |
| Риск (`FraudDetected`) | `rideId` | 12 | средняя частота |
| Сага/состояние | `sagaId` | 12 | порядок шагов процесса |

Правило выбора ключа: **ключ = идентификатор сущности**, изменения которой должны обрабатываться
по порядку. Ключ не должен быть случайным (иначе теряется порядок) и не должен быть единым
(иначе теряется параллелизм).

### Топики и хранение (retention)

| Топик | Retention | Дополнительно |
|---|---|---|
| `<jurisdiction>.driver.driver-location-updated.v1` | 6 часов | плюс компактированный `<jurisdiction>.driver.driver-location-latest.v1` для последней позиции |
| `<jurisdiction>.booking.booking-created.v1`, `ride-*` | 30 дней | архив в ClickHouse для аналитики |
| `<jurisdiction>.payments.*`, `<jurisdiction>.payouts.*` | 365 дней | хранение для обработки и повторов; долгосрочный неизменяемый аудит - в append-only хранилище БД (>= 5 лет, NFR-FS-06) |
| `<jurisdiction>.pricing.*` | 7 дней | пересчитывается из состояния |
| `<jurisdiction>.booking.driver-offer-*.v1` | 24 часа | короткоживущие офферы; replay не нужен |
| `<jurisdiction>.driver.driver-offer-*.v1` | 24 часа | ответы водителя (accept/decline) |
| `<jurisdiction>.booking.driver-search-*.v1` | 7 дней | наблюдаемость диспетчеризации |
| `<jurisdiction>.geography.zone-balance-updated.v1` | компактированный | последний баланс зоны |
| `<jurisdiction>.geography.zone-deficit-detected.v1` | 7 дней | сигналы дефицита |
| `<jurisdiction>.analytics.demand-forecast-updated.v1` | 7 дней | прогноз спроса (Flink, домен Analytics) |
| Сага-топики | компактированные (log compaction) | хранят последнее состояние шага |

### Оценка ёмкости (геопозиции)

- Пиковый поток `DriverLocationUpdated` (NFR-FL-02): 5 000 000 / мин, то есть ~83 000 сообщений/с.
- Retention 6 ч: 5 000 000 x 60 x 6 = ~1,8 млрд сообщений в окне хранения на регион.
- При среднем сообщении ~200 байт это ~360 ГБ, с фактором репликации 3 - ~1,1 ТБ на регион.
- 48 партиций дают ~83 000 / 48 = ~1 700 сообщений/с (~0,35 МБ/с) на партицию - с запасом.
- Компактированный `<jurisdiction>.driver.driver-location-latest.v1` хранит только последнюю позицию
  на водителя и по объёму незначителен.

Оценка порядка величин; уточняется нагрузочным тестом.

### Надёжность хранения

- Replication factor = 3 внутри региона (по зонам доступности).
- `min.insync.replicas = 2`; продюсеры пишут с `acks=all`.
- Schema Registry - **единый глобальный реестр схем** (схемы не содержат персональных данных);
  субъекты схем именуются по регионам: `<jurisdiction>.<topic>-value`.

### Межрегиональное взаимодействие

- Основной режим - **юрисдикция-локальный**: события обрабатываются в пределах страны.
- **Внутри юрисдикции** бизнес-топики зеркалируются **односторонне из primary в standby**
  (MirrorMaker 2: `IdentityReplicationPolicy`, checkpoint-коннектор для трансляции смещений).
  Так второй регион видит те же события и после failover продолжает с сохранённых offsets.
  Направление меняется вместе со сменой primary/standby, поэтому встречного зеркалирования и
  петель нет.
- Между юрисдикциями допускается зеркалирование только справочных и обезличенных агрегатных
  топиков.
- Данные резидентов **не покидают страну**; наружу выносятся только агрегаты без персональных
  данных.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Топик на юрисдикцию, кластеры в двух её регионах с зеркалированием бизнес-топиков (выбрано) | изоляция по странам, data residency, продолжение обработки при отказе региона | больше топиков, дублирование конфигурации | Принято |
| Один глобальный топик, регион в ключе партиции | проще эксплуатация | данные разных стран в одном кластере, нарушение data residency, "шумный сосед" | Отклонено |
| Кластеры по регионам без зеркалирования внутри юрисдикции | проще | второй регион не видит бизнес-события первого, failover без истории и offsets | Отклонено |
| Партиционирование по случайному ключу | равномерная нагрузка | нет порядка по сущности | Отклонено |

## Недостатки, ограничения и риски

- **Рост числа топиков**: на каждую юрисдикцию и тип события - свой топик; нужны шаблоны и
  автоматизация создания (IaC, см. Task1/ADR-004).
- **Глобальный Schema Registry - общая зависимость**: при его недоступности публикация новых
  схем и продюсеры испытывают трудности. Митигация: отказоустойчивое развёртывание реестра
  (несколько экземпляров минимум в двух зонах/регионах, автоматический failover), резервные
  копии с RPO/RTO уровня платформы и кэширование уже полученных схем у клиентов - потребители
  продолжают работать на кэше. Схемы не содержат персональных данных, поэтому размещение
  реестра вне домашнего региона не нарушает требования.
- **Горячие партиции**: популярный водитель или зона могут перегрузить одну партицию;
  митигируется мониторингом (см. ADR-006) и дроблением ключа при необходимости.
- **Межрегиональная репликация**: только для агрегатов, иначе растёт стоимость и появляются
  требования по комплаенсу.

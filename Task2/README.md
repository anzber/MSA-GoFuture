# Task 2. Проектируем Event-Driven архитектуру "GoFuture"


## 1. Контекст

Монолит не справляется с 500 тыс. конкурентных поездок и не умеет считать динамические цены
в реальном времени. Нужна распределённая событийная платформа, где домены обмениваются
событиями, а не синхронными вызовами, и где поток событий можно обрабатывать в реальном времени.

## 3. Решение на одном экране

1. **Шина событий - Kafka.** Все домены публикуют и читают доменные события. Событие - это факт
   в прошедшем времени (`BookingCreated`, `DriverLocationUpdated`, `PaymentCaptured`).
2. **Топики партиционированы по юрисдикциям.** Топик на юрисдикцию (`<jurisdiction>.<domain>.<event>.v1`),
   внутри порядок обеспечивается ключом сущности (`ride_id`, `driver_id`).
3. **Обработка в реальном времени** - Kafka Streams (баланс зон `ZoneBalance`, ETA, агрегаты) и
   Flink (тяжёлая потоковая аналитика, ML-фичи для фрода и прогноз спроса).
4. **Умное перераспределение водителей** - `ZoneBalance` считает спрос/предложение и дефицит зон;
   Booking ведёт окно подбора и шлёт `DriverOfferCreated` с TTL, ранжируя кандидатов по ETA,
   дефициту зоны и прогнозу спроса (см. ADR-004). Динамическая цена `PriceUpdated` остаётся
   за Pricing - правило "один тип события - один владелец" соблюдено.
5. **Saga - оркестрация** для жизненного цикла поездки и денег (ветвистый долгоживущий процесс),
   **хореография** - для простых реакций (уведомления, аналитика).
6. **Надёжная доставка** - transactional outbox + CDC, at-least-once, идемпотентные потребители,
   ретраи с backoff и DLQ.
7. **Мониторинг** - OpenTelemetry Collector, Prometheus, Grafana, Loki, Jaeger, Alertmanager;
   метрики: задержка доставки, consumer lag, размер DLQ, доля ошибок и др.

## 4. Ключевые компромиссы

| Решение | Почему | Компромисс/риск |
|---|---|---|
| Событийная интеграция вместо синхронных вызовов | развязка доменов, масштаб, realtime | итоговая согласованность, сложнее отладка |
| Топик на регион | изоляция нагрузки, данные в регионе (data residency) | больше топиков и инфраструктуры |
| Оркестрация Saga в Booking | прозрачность и аудит процесса | Booking становится критичным координатором |
| at-least-once + идемпотентность вместо exactly-once | проще и надёжнее в эксплуатации | нужны дедупликация и идемпотентные обработчики |
| Своя шина на Kafka | в лендскейпе уже есть RabbitMQ, но нужен realtime-поток | операционная сложность Kafka |

# ADR-006 (Task2). Подход к мониторингу, метрики и инструменты

## Общая информация

1. **Родительский артефакт** - `ADR-001..ADR-005` (события, топики, потребители, сага, доставка);
   лендскейп кейса (Prometheus, Grafana, Loki, Alertmanager); теория (OpenTelemetry, Jaeger).
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.

## Контекст

Событийная платформа распределена: события проходят через шину, потоковые обработчики и несколько
сервисов. Сбой или задержку сложно заметить "на глаз". Нужен подход к мониторингу, измеримые
метрики и конкретные инструменты, отражённые на диаграмме C2.

## Требования

| No. | Требование |
|---|---|
| 1 | 100 % критических сервисов и обработчиков покрыты метриками и алертами. |
| 2 | Видно отставание потребителей и "застревание" саг. |
| 3 | Сквозная трассировка цепочки событий. |
| 4 | Алерты привязаны к SLO (ухудшение доступности обработки), а не к шуму. |
| 5 | Инструменты интегрированы в целевую архитектуру (C2). |

## Решение

### Подход

1. **Четыре золотых сигнала** для сервисов и обработчиков: задержка (latency), трафик (traffic),
   ошибки (errors), насыщение (saturation).
2. **Специфика событийной платформы**:
   - отставание потребителей (`consumer lag`) по каждой группе, топику и партиции;
   - отставание outbox и задержка публикации;
   - размер и скорость роста DLQ;
   - число и длительность саг, застрявшие саги (нет ожидаемого события в тайм-аут);
   - сквозная задержка события (от `occurredAt` до успешной обработки).
3. **Сквозная трассировка**: `correlationId` протаскивается через события, поэтому цепочку
   "заказ -> оплата -> выплата" видно в трейсе.
4. **Структурированные логи** с `correlationId`, `region`, `eventType`.
5. **Алертинг по SLO**: алерт на ухудшение доступности обработки и на выгорание бюджета ошибок;
   контролируется доля ложных срабатываний.

### Список метрик

| Метрика | Что показывает | Где снимается | Ориентир |
|---|---|---|---|
| `kafka_consumergroup_lag` | отставание потребителей | Kafka / потребители | не растёт устойчиво, выше порога - алерт |
| `outbox_backlog_age_seconds` | возраст непубликованных событий | БД сервиса / CDC | секунды |
| `event_publish_errors_total` | ошибки публикации | продюсеры | 0 в норме |
| `event_e2e_latency_seconds` | задержка от события до обработки (p95) | потребители (по correlationId) | <= 3 с |
| `price_update_latency_seconds` | задержка пересчёта цены | Kafka Streams | <= 5 с |
| `dlq_messages_total` | события в необработанной очереди | DLQ-топики | 0, рост - алерт |
| `consumer_processing_errors_total` | ошибки обработки | потребители | доля от общего потока |
| `consumer_rebalances_total` | перебалансировки групп | потребители | редко |
| `saga_duration_seconds` | длительность саги | оркестратор (Booking) | в пределах нормы |
| `saga_stuck_total` | застрявшие саги | оркестратор | 0 |
| `dispatch_time_to_assign_seconds` | время от заявки до назначения (p95) | Booking (диспетчеризация) | в пределах NFR-PE-04 |
| `driver_offer_accept_rate` | доля принятых офферов | Booking / Driver | растёт при корректном скоринге |
| `offers_per_assignment` | число офферов на одно назначение | Booking | низкое |
| `dispatch_fallback_total` | срабатывания fallback (ближайший водитель) | Booking | минимум |
| `zone_deficit_ratio` | соотношение спроса и предложения по зонам | ZoneBalance (KStreams) | управляемый |
| `hot_zone_concentration` | доля водителей в топ-10 % зон | ZoneBalance | в пределах NFR-FS-08 |
| `pickup_wait_seconds` | ожидание подачи после назначения | Booking | в пределах SLA |
| `payment_capture_rate` | доля успешных оплат | Payments | бизнес-ориентир |
| `kafka_under_replicated_partitions` | недореплицированные партиции | брокер | 0 |
| `kafka_disk_usage_ratio` | заполнение диска | брокер | ниже порога |
| `flink_checkpoint_duration_seconds` | контрольные точки Flink | Flink | в пределах нормы |
| `service_availability` (SLO) | доступность обработки | сервисы/обработчики | >= целевого |

### Инструменты (отражение на диаграмме C2)

| Инструмент | Роль | На C2 |
|---|---|---|
| **OpenTelemetry Collector** | единый сбор метрик, логов, трейсов со всех сервисов | контейнер "OpenTelemetry Collector" |
| **Prometheus** | приём и хранение метрик, правила алертов | контейнер "Prometheus" |
| **Grafana** | дашборды и визуализация | контейнер "Grafana" |
| **Loki** | агрегация логов | контейнер "Loki" |
| **Jaeger** | распределённые трейсы (цепочки событий) | контейнер "Jaeger" |
| **Alertmanager** | маршрутизация и отправка алертов | контейнер "Alertmanager" |
| **Schema Registry** | мониторинг ошибок сериализации и совместимости схем | контейнер "Schema Registry" |

Поток: `сервисы и обработчики -> OpenTelemetry Collector -> Prometheus / Loki / Jaeger ->
Grafana (дашборды); Prometheus -> Alertmanager -> дежурный`.

### Обоснование выбора

- **Prometheus, Grafana, Loki, Alertmanager** уже есть в лендскейпе компании, поэтому их
  переиспользуем.
- **OpenTelemetry** и **Jaeger** добавляем из теории: без распределённой трассировки событийную
  цепочку через несколько сервисов не отладить.
- Все инструменты вендор-нейтральны и собираются с Kafka, Kafka Streams и Flink.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| OTel + Prometheus/Grafana + Loki + Jaeger (выбрано) | переиспользуем лендскейп + открытые стандарты | несколько инструментов | Принято |
| ELK (Elasticsearch/Kibana) для логов и трейсов | единый стек | Elasticsearch уже используется для геопоиска, смешение нагрузок | Отклонено |
| Zipkin вместо Jaeger | проще | Jaeger уже упоминается в теории | Отклонено |
| Облачный APM (SaaS) | быстрый старт | стоимость, данные вне периметра | Отклонено |
| Мониторинг только брокера | минимум усилий | не видно обработки и бизнес-эффектов | Отклонено |

## Недостатки, ограничения и риски

- **Кардинальность метрик**: `consumer lag` по всем группам/топикам/партициям может быть
  большим; нужны агрегаты и разумные лейблы.
- **Трассировка потоковых задач**: сквозной трейс через Kafka Streams/Flink требует ручной
  передачи контекста; настраивается отдельно.
- **Алертный шум**: без настройки порогов алерты по lag и DLQ быстро утомляют дежурных;
  поэтому привязка к SLO и контроль ложных срабатываний.
- **Стоимость хранения логов и трейсов**: нужны политики хранения и выборка (часть трейсов,
  а не все).

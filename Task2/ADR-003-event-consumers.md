# ADR-003 (Task2). Потребители событий: Kafka Streams и Flink

## Общая информация

1. **Родительский артефакт** - `ADR-001-domain-events.md`, `ADR-002-kafka-topics.md`.
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.

## Контекст

События нужно не только "раздавать" сервисам, но и обрабатывать потоково и в реальном времени:
считать динамические цены, определять спрос по зонам, готовить признаки для ML-моделей
(прогноз спроса, фрод). Для этого нужны потоковые обработчики. В задании названы Kafka Streams
(KStreams) и Flink.

## Требования

| No. | Требование |
|---|---|
| 1 | Обработка событий в реальном времени (динамическая цена обновляется <= 5 с). |
| 2 | Горизонтальное масштабирование обработки. |
| 3 | Обработка должна быть отказоустойчивой и перезапускаемой с сохранением состояния. |
| 4 | Поддержка оконных вычислений (агрегаты по времени) и учета времени события. |
| 5 | Разделение лёгких доменных задач и тяжёлой аналитики/ML. |

## Решение

Используются **три класса потребителей**, каждый для своей задачи:

### 1. Сервисные потребители (обычный Kafka consumer)

Доменные сервисы читают нужные им топики и реагируют (например, Notification отправляет
уведомление, Payments обрабатывает `RideCompleted`). Простая логика "событие -> реакция",
без потоковых вычислений.

### 2. Kafka Streams (KStreams) - доменные потоковые задачи

Для задач, которые живут рядом с доменом и требуют состояния:
- **баланс зон** (задача `ZoneBalance`, владелец - Geography): тепловая карта спроса и
  предложения (сколько заказов и водителей по зонам), дефицит зоны, агрегаты для умного
  перераспределения. Результат публикуется как `ZoneBalanceUpdated` (компактированный) и
  `ZoneDeficitDetected`;
- обновление **ETA** и признаков для матчинга;
- потоковые счётчики и агрегаты по поездкам.

> Динамическую цену Kafka Streams **не публикует**: `PriceUpdated` - событие Pricing (владелец из
> ADR-001). Pricing потребляет `ZoneDeficitDetected` / `ZoneBalanceUpdated` и считает цену сам,
> поэтому правило "один тип события - один владелец-продюсер" соблюдено.

Почему Kafka Streams: библиотека, встраиваемая в сервис; состояние в local state store,
поддерживается через changelog-топики; окна и aggregation "из коробки"; нет отдельного кластера.

### 3. Flink - тяжёлая потоковая аналитика и ML-признаки

Для задач аналитики и ML:
- агрегаты и витрины реального времени в ClickHouse;
- расчёт признаков для ML-моделей (прогноз спроса, обнаружение фрода);
- прогноз спроса по зонам (`DemandForecastUpdated`) - вход для скоринга диспетчеризации;
- обработка больших окон и сложные операции соединения потоков.

Почему Flink: работа по времени события (event time) с водяными знаками, состояние большого
объёма, точная обработка (exactly-once) и зрелый операционный опыт для тяжёлых потоков.

### Итого поток обработки

```
Домены -> Kafka (топики по регионам)
            |-> сервисные потребители (реакции, шаги саги)
            |-> Kafka Streams (топологии доменов: Pricing - цены; Geography - баланс зон и ETA) -> публикация доменом-владельцем (PriceUpdated, ZoneBalanceUpdated, ZoneDeficitDetected)
            |-> Flink (аналитика, ML-признаки) -> ClickHouse, ML-платформа
```

### Параметры потребителей

- Каждый потребитель - в своей **группе потребителей** (`consumer group`), масштабируется
  добавлением экземпляров до числа партиций.
- Смещения (offset) хранятся в Kafka; фиксация - после успешной обработки (at-least-once).
- Идемпотентность обработки - обязательна (см. ADR-005).
- Отставание потребителей (`consumer lag`) - ключевая метрика (см. ADR-006).

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Kafka Streams + Flink (выбрано) | каждому классу задач - свой инструмент | две технологии в эксплуатации | Принято |
| Только Kafka Streams | одна технология, проще | тяжёлые окна/большое состояние менее удобны | Отклонено |
| Только Flink | единая потоковая платформа | тяжелее для лёгких доменных задач, отдельный кластер, выше порог входа | Частично (для аналитики/ML) |
| Только обычные потребители | простота | нет агрегатов и окон, ручная реализация состояния | Отклонено |
| Spark Streaming | знаком команде (есть в лендскейпе Spark) | микробатчи, выше задержка для realtime | Отклонено для realtime, допустимо для пакетной аналитики |

## Недостатки, ограничения и риски

- **Две технологии** (Kafka Streams и Flink) увеличивают требования к компетенциям и
  эксплуатации; митигируется разделением зон ответственности (домен - Streams, аналитика - Flink).
- **Состояние потоковых задач** требует changelog-топиков и места; при сбое - восстановление
  из state store и changelog, возможен временный рост lag.
- **Порядок только в партиции**: при репартиционировании (например, агрегация по зоне, где
  ключ отличается от исходного) порядок по сущности может теряться; это учитывается в логике задач.
- **Стоимость**: потоковая обработка всегда включена и потребляет ресурсы даже при малой
  нагрузке; митигируется автомасштабированием, привязанным к lag (см. ADR-006).

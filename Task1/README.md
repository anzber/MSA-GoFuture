# Task 1. Проектируем домены: поэтапная декомпозиция монолита "GoFuture"

> Итоговый проект, спринт 6. Автор: Анзор Березгов, архитектор. Дата: 28.09.2026.
> Исходные материалы кейса - в [`source/`](source/): `C1.puml`, `C2.puml`, `C3.puml` и их отрисовки.

## 1. Контекст

"GoFuture" - платформа агрегирования такси: пассажирское и водительское приложения,
веб-портал для корпоративных клиентов. Сейчас это **монолит на Django** с единой БД
PostgreSQL, Celery/RabbitMQ для фоновых задач и ручным вертикальным масштабированием.
Бизнес упирается в ограничения монолита:

- пиковые нагрузки > 100 тыс. активных поездок вызывают каскадные отказы;
- MTTR > 4 часов, разработка функции >= 6 месяцев;
- нет горизонтального масштабирования и выхода в новые регионы (SEA, LatAm);
- регуляторные требования разных стран невозможно выполнить в единой БД.

**Цель проекта** - перейти к доменно-ориентированной микросервисной архитектуре за год,
обеспечив: 500 тыс. конкурентных поездок, 99,95 %+ доступности критичных сервисов,
time-to-market <= 2 недель, горизонтальное масштабирование в >= 3 регионах, соответствие
локальным регуляторикам.

## 3. Решение на одном экране

1. **Домены = продуктовые команды.** Восемь доменов (Booking, Driver, Pricing, Payments,
   Notification, Geography, Analytics, Fraud) соответствуют восьми продуктовым командам.
   Выплаты водителям выделены в отдельный сервис **Payouts** внутри домена Payments
   (другие транзакционные гарантии и регуляторные требования, чем у входящих платежей),
   но остаются ответственностью команды Payments.
2. **Database-per-service.** Каждый сервис владеет своей БД; прямые запросы в чужие БД
   запрещены. Общая БД монолита существует только на время STRANGLER-миграции.
3. **Слой обратной совместимости** - ключевой механизм бесшовного перехода:
   API Gateway / BFF как Strangler Facade, Anti-Corruption Layer (ACL), версионирование
   API, реестр схем событий (BACKWARD_TRANSITIVE), CDC/Debezium и transactional outbox.
4. **Шесть волн за 12 месяцев**: фундамент -> "быстрые" сервисы (Notification, Analytics) ->
   Geography, Fraud -> Driver, Pricing -> Booking, Payments -> Payouts + вывод монолита.
5. **Миграция данных** по единой схеме `расширение схемы -> первичная загрузка -> CDC (log-based) ->
   параллельное чтение -> переключение по региону -> сверка -> вывод из эксплуатации`
   с обратной совместимостью на каждом шаге.

## 4. Ключевые архитектурные решения и компромиссы

| Решение | Почему | Компромисс / риск |
|---|---|---|
| Strangler Fig вместо "big bang" | нет длительного простоя; бизнес работает во время миграции | переходный период дольше; нужна дисциплина по срокам |
| Database-per-service | независимость команд, изоляция отказов, масштабирование | отказ от распределённых транзакций -> eventual consistency, Saga |
| API Gateway + BFF | скрывает перестройку доменов от мобильных клиентов | gateway - критичный компонент, нужен отказоустойчивый кластер |
| Kafka как шина событий | 500 тыс. поездок, realtime-ценообразование, интеграция | операционная сложность, нужен Schema Registry и DQ |
| Разбиение по DDD-границам | минимум связанности, автономия команд | требует времени на выравнивание моделей (event storming) |

## 5. Допущения и трактовки

- **Доступность.** В описании кейса встречаются 99,95 % (Задание 1) и 99,99 % (Задание 3).
  В NFR принята единая шкала: критические сервисы - 99,99 % (бизнес-минимум кейса 99,95 %
  выполняется с запасом), остальные сервисы - 99,95 %. Трактовка принята как рабочее допущение.
- **Payouts.** В лендскейпе указаны 8 команд и 8 доменов, но в C3 присутствует отдельный
  доменный компонент `Payouts Domain`. Принято решение выделить его как отдельный **сервис
  в границах домена Payments** - так команда остаётся одна, а транзакционные/регуляторные
  границы соблюдены.
- **Технологии.** Целевой стек доменных сервисов - Go (производительность, низкое потребление
  памяти) там, где важна latency; допустимо оставлять Python там, где команда уже сильна
  (Fraud/ML). Выбор конкретного языка - вторичен относительно границ доменов.
- **Срок.** План рассчитан на 12 месяцев; волны пересекаются (разные команды работают
  параллельно), но зависимости между волнами учтены.

## 6. Навигация по диаграмме C2 To-Be

На `C2_ToBe_GoFuture.png`:
- **жёлтым** выделен "Слой обратной совместимости" (API Gateway/Strangler, ACL);
- **красным (пунктиром)** - легаси-монолит и его БД, выводимые из эксплуатации;
- доменные сервисы сгруппированы в один boundary "по продуктовым командам";
- справа - платформа (IAM, Config, шина событий), хранилища и Observability/CI-CD.

Легенда и пояснения к обратной совместимости - прямо на диаграмме.

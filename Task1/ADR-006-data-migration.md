# ADR-006. План миграции данных при декомпозиции монолита

## Общая информация

1. **Родительский артефакт** - `ADR-003-extraction-order.md`, `ADR-005-backward-compatibility.md`.
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.
4. **Согласующие** - команды доменов, DBA, SRE, команда безопасности, финансовый отдел.

## Контекст

Переход к database-per-service требует перенести данные из общей `legacy_db` (PostgreSQL)
и сопутствующих хранилищ (`Redis`, `Elasticsearch`, `ClickHouse`) в изолированные БД сервисов.
Объёмы большие (более 500 тыс. конкурентных поездок, многолетняя история), а часть данных -
**финансовые** (платежи, выплаты, балансы): их нельзя "потерять" или продублировать.
При этом продукт работает 24/7, и остановка записи на часы недопустима (NFR-RE-01, NFR-MM-04).

Дополнительные ограничения:

- данные резидентов должны оставаться в своём регионе (NFR-SE-01);
- PII нельзя копировать "куда попало" без контроля (NFR-SE-03, NFR-SE-06);
- в монолите сохраняются прямые SQL-связи между доменами (`C3.puml`), значит переносить
  нужно согласованно, а не по одной таблице.

## Требования

| No. | Требование |
|---|---|
| 1 | Миграция без длительного простоя записи (NFR-MM-04). |
| 2 | Отсутствие расхождений: ежедневная сверка с нулевым расхождением (NFR-FS-05). |
| 3 | Идемпотентность: повторный прогон миграции не создаёт дублей (NFR-FS-03). |
| 4 | Возможность отката (rollback) на каждом шаге без потери данных. |
| 5 | Соблюдение data residency и защита PII при переносе (NFR-SE-01, NFR-SE-03). |
| 6 | Финансовые данные - append-only, неизменяемый аудит >= 5 лет (NFR-FS-06). |

## Решение

### Единая стратегия: Расширение схемы -> Первичная загрузка -> Двойная запись/CDC -> Параллельное чтение -> Переключение -> Сверка -> Вывод из эксплуатации

| Фаза | Что делаем | Инструменты | Совместимость |
|---|---|---|---|
| **0. Inventory & ownership** | Инвентаризация таблиц, ответственные, объёмы, PII-классификация | Data catalog | - |
| **1. Expand** | В БД сервиса создаём целевую схему; легаси-код и схему не меняем | Flyway/Liquibase | Легаси не меняется |
| **2. Первичная загрузка** | Исторические данные переносим батчами с throttling | `COPY`/`pg_dump`, Airflow/Spark, dbt | Легаси продолжает жить |
| **3. CDC (log-based, Debezium)** | Текущие изменения из легаси идут в Kafka через **Debezium** - чтение WAL (log-based CDC), без записи в легаси. Outbox-таблица в легаси не нужна; монолит пишет свои таблицы как раньше, а новые сервисы используют transactional outbox + релей для своих событий | Debezium, Kafka Connect | Легаси - источник правды |
| **4. Параллельное чтение** | Новый сервис читается параллельно с монолитом, ответы сравниваются; пользователь ещё на монолите | Canary + diff-мониторинг | Расхождения не влияют на клиента |
| **5. Cutover** | Переключение чтения, затем записи - **по регионам/сегментам**, не глобально. Для денег - короткое окно заморозки операций (не более минут) | Feature flags, Gateway routing | Мгновенный откат флагом |
| **6. Reconcile** | Сверка: количество строк, контрольные суммы, бизнес-инварианты (сумма балансов, число поездок, обороты). Ежедневно, пока не 0 | Reconciliation-джобы, dbt-тесты | Источник правды - сервис |
| **7. Decommission** | Легаси-таблицы переводятся в read-only view, затем удаляются после периода обкатки | Миграции | Полная независимость |

### План миграции по сервисам

| Сервис | Исходные данные (legacy) | Целевое хранилище | Особенности объёма | Метод | Cutover | Верификация |
|---|---|---|---|---|---|---|
| **Notification** | `notifications`, `notification_templates`, `devices`, `push_tokens` | Notification DB (PostgreSQL + Redis) | Большой поток, короткий срок жизни части данных | Первичная загрузка + CDC из легаси | По шаблонам/типам уведомлений, затем полный | Сверка счётчиков отправок; сравнение API-ответов |
| **Analytics** | Spark/ETL-выгрузки, `reporting_*`, ClickHouse `analytics_db` | Analytics DW (ClickHouse) + витрины | Историческая аналитика (ТБ) | Replay событий из Kafka + пакетная первичная загрузка | Analytics не влияет на прод; переключение по готовности витрин | Пересчёт контрольных агрегатов, сверка с legacy-отчётами |
| **Fraud** | `fraud_rules`, `blacklist`, `risk_profiles`, выгрузки проверок | Fraud DB (PostgreSQL + Redis) | Средний объём, но критична свежесть | Первичная загрузка правил + event-потребитель | По региону; сначала "режим советника", потом блокирующий | Метрики срабатываний, сверка вердиктов на исторических кейсах |
| **Geography** | `drivers` (гео), `zones`, гео-кеш | Geo Index (PostGIS/Elasticsearch) | Геоиндекс пересобираем из источника | Reindex + поток `DriverLocationUpdated` | По регионам, постепенно переводя трафик поиска | Сравнение результатов поиска/ETA, доля найденных водителей |
| **Driver** | `drivers`, `vehicles`, `driver_documents`, `driver_ratings`, `shifts` | Driver DB (PostgreSQL) | Большая история поездок/заказов, PII | Первичная загрузка + CDC | По регионам, приём заказов в новом сервисе | Сверка рейтингов, документов, активных водителей |
| **Pricing** | `tariffs`, `pricing_rules`, `dynamic_price_state`, `price_history` | Pricing DB + Redis cache | Небольшая БД, высокая частота чтения | Первичная загрузка + CDC; прогрев кэша | Переключение котировок по городам/регионам | Сравнение цен на потоке запросов, параллельный расчёт цены |
| **Payments** | `payments`, `transactions`, `refunds`, `payment_methods` (токены PSP) | Журнал операций Payments (append-only PostgreSQL) | Финансы, PCI, идемпотентность | Первичная загрузка + CDC из легаси; далее запись в сервисе через transactional outbox; токены остаются у PSP | **Короткое окно заморозки**, по регионам/валютам | Полная сверка: суммы, число операций, сверка с PSP и журнала операций |
| **Payouts** | `payouts`, `driver_balances`, `payout_transactions`, `bank_accounts` | Журнал операций Payouts (append-only PostgreSQL) | Финансы, банковские реквизиты (PII) | Первичная загрузка балансов на "снимок" + CDC | Заморозка выплат на окно, затем переключение | Балансы водителей, сверка с банком, сверка журнала операций |
| **Booking** | `bookings`, `offers`, `rides`, `ride_events` | Booking DB (PostgreSQL, партиции по регионам) | **Самый большой объём**, реальное время | Партиционированная первичная загрузка + CDC; партиции по региону | По регионам, с "двойным чтением" и флагами | Число поездок, статусы, события; сверка по регионам |

### Партиционирование и масштаб (большой объём данных)

- Таблицы Booking/Payments/Payouts **партиционируются** по региону и времени (range partitioning);
  миграция идёт партициями - это позволяет переключать регион целиком и откатывать его отдельно.
- Первичная загрузка выполняется на **read-репликах** легаси, чтобы не нагружать мастер (CDC тоже читает
  через выделенный replication-слот).
- Для геоиндекса (Elasticsearch) применяется **reindex/aliases**: новый индекс наполняется
  параллельно, переключение alias - атомарно.
- Для ClickHouse - запись через Kafka-коннектор и повторный пересчёт витрин (idempotent).

### Сверка (reconciliation)

1. **Техническая:** количество строк, контрольные суммы (checksums) по таблицам.
2. **Бизнес:** инварианты - сумма балансов водителей = сумма операций журнала; число завершённых
   поездок = число списаний; обороты = сверка с PSP/банком.
3. **Непрерывная:** в период обкатки reconciliation запускается ежедневно; при расхождении -
   алерт и автоматическая остановка cutover.

### Совместимость на время миграции

- Легаси-таблицы на переходный период доступны сервисам через **read-only views/read-models**
  (ADR-005), поэтому старые потребители не ломаются.
- Каждый переключённый объект защищён **feature flag** и может быть откачен на монолит.
- Данные, перенесённые в сервис, больше **не пишутся монолитом**; любые изменения - только
  через API сервиса.

### Комплаенс, PII и регионы

- **Data residency:** данные резидентов переносятся в хранилище региона проживания (NFR-SE-01);
  для мультирегиона (Task3) миграция сразу раскладывается по региональным кластерам.
- **PII:** при переносе - шифрование at-rest, маскирование в логах, ограниченный доступ (NFR-SE-03, NFR-SE-06);
  после переноса персональные данные удаляются из легаси в рамках decommission.
- **Финансовый аудит:** таблицы журнала операций append-only, неизменяемая история >= 5 лет (NFR-FS-06).

### Инструменты

| Задача | Инструмент |
|---|---|
| Изменения схем | Flyway / Liquibase (expand-contract) |
| Захват изменений | Debezium + Kafka Connect (log-based CDC по WAL) |
| Оркестрация первичной загрузки | Airflow / dbt / Spark |
| Потоки и витрины | Kafka, Flink, ClickHouse |
| Геоиндекс | Elasticsearch reindex + aliases |
| Сверка | Собственные reconciliation-джобы + dbt-тесты |

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| **Expand/CDC/cutover (выбрано)** | Без простоя, откатываемо, проверяемо | Инфраструктура (Debezium, реестр), сложность | Принято |
| Остановка записи и `pg_dump`/restore | Просто, консистентно | Простой на часы - недопустим (NFR-RE-01, NFR-MM-04) | Отклонено |
| Только dual-write из бизнес-кода | Не нужен CDC | Правки легаси-кода, расхождения, дубли | Отклонено |
| Переносить всё "одним куском" на финале | Меньше промежуточных состояний | Монолитный риск, максимальный простой | Отклонено |
| Копировать всю БД целиком в каждый сервис | Просто | Нарушает database-per-service и владение данными | Отклонено |

## Недостатки, ограничения и риски

- **Расхождения при CDC-проекции** - главный риск. Митигируется чтением из WAL (Debezium) вместо
  прямой двойной записи, регулярной сверкой и остановкой cutover при расхождении.
- **CDC-лаг** под пиковой нагрузкой. Митигируется отдельными репликами, мониторингом lag,
  backpressure и ограничение скорости первичной загрузки.
- **Финансовое окно заморозки** (Payments/Payouts) всё же необходимо - короткое (минуты), в
  часы низкой нагрузки, с планом коммуникации для поддержки и партнёров.
- **Bookings - самый тяжёлый объект.** Ошибка в переключении региона влияет на реальные поездки;
  поэтому переключение по регионам, с параллельным чтением и мгновенным откатом.
- **Очистка легаси откладывается** до подтверждённой сверки - на переходном периоде хранится
  "двойной" объём данных, что увеличивает стоимость хранения (учитывается в FinOps, NFR-BC-01).
- **PII-риски при копировании.** Митигируется классификацией данных, шифрованием и удалением
  из легаси сразу после decommission.

# ADR-005. Механизмы обеспечения обратной совместимости при декомпозиции

## Общая информация

1. **Родительский артефакт** - `ADR-004-tobe-c2-services.md`, `ADR-002-domain-service-map.md`.
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.
4. **Согласующие** - продуктовые команды, мобильные команды (iOS/Android/HMS), SRE.

## Контекст

Декомпозиция идёт **постепенно, на работающем продукте**. Пока сервис не выделен полностью,
одновременно существуют:

- старые мобильные приложения (iOS/Android/Huawei), которые нельзя обновить синхронно
  с бэкендом (NFR-CO-03);
- корпоративные интеграции и веб-портал, завязанные на текущие REST-эндпоинты;
- остаток монолита, который ещё владеет частью данных;
- новые доменные сервисы со своими контрактами и событиями.

Без явных механизмов обратной совместимости любой релиз во время миграции будет "ломать"
часть клиентов, а команды - блокировать друг друга. Требуется набор правил и технических
средств, делающих переход невидимым для потребителей.

## Требования

| No. | Требование |
|---|---|
| 1 | Старые клиенты продолжают работать без принудительного обновления (NFR-CO-03). |
| 2 | Внутри мажорной версии API - только аддитивные изменения; удаление - через деприкейшн (NFR-CO-01, NFR-CO-02). |
| 3 | Схемы событий совместимы в обратном направлении (NFR-CO-04). |
| 4 | Независимый деплой сервисов не требует синхронного релиза всех потребителей (NFR-MM-02). |
| 5 | Переход данных из монолита в сервис не требует остановки записи в легаси. |
| 6 | Возможность быстрого отката волны без потери данных. |

## Решение

Обратная совместимость обеспечивается **на четырёх уровнях**: маршрутизация, контракты,
данные и релизы.

### Уровень 1. Маршрутизация и API

| Механизм | Как работает | Что закрывает |
|---|---|---|
| **Strangler Facade (API Gateway)** | Публикует не меняющиеся URL; маршрутизирует в новый сервис или в монолит в зависимости от готовности домена | Бесшовность миграции без остановки клиентов |
| **Dual-routing + fallback** | Если новый сервис недоступен/не выделен - запрос идёт в монолит; после выделения - можно включить fallback обратно на период обкатки | Снижение риска волны, быстрый откат |
| **Версионирование API** (`/v1`, `/v2`, gRPC `package.v1`) | Новая функциональность - новая версия; старая живёт параллельно | Совместимость API для старых клиентов |
| **Деприкейшн-политика** | Заголовки `Deprecation`, `Sunset`; окно >= 2 релиза / 90 дней; журнал использования версий | Предсказуемый вывод API из эксплуатации |
| **BFF (Backend-for-Frontend)** | Отдельная адаптация контракта под пассажирский/водительский/корпоративный клиент; скрывает перестройку доменов | Совместимость контрактов под разные типы клиентов |
| **Минимальная поддерживаемая версия приложения** | Сервер знает `min_supported_version`; старые версии работают >= 6 месяцев | Работа старых версий приложений |

### Уровень 2. Контракты и тестирование

| Механизм | Как работает | Что закрывает |
|---|---|---|
| **Consumer-Driven Contract Testing (Pact)** | Каждый потребитель публикует контракт; CI обеих сторон проверяет совместимость | Предотвращает breaking changes |
| **Schema Registry (Avro/Protobuf)** | Реестр схем событий с режимом `BACKWARD_TRANSITIVE`; CI блокирует несовместимую эволюцию | Совместимость схем событий |
| **Envelope событий** | `{eventType, version, region, occurredAt, payload}`; потребители игнорируют неизвестные поля | Добавление полей без слома потребителей |
| **OpenAPI/Protobuf как единый источник правды** | Контракт-файл генерирует клиентов и серверные заглушки, диффы - в code review | Единый источник правды по контрактам |
| **Fitness-functions в CI** | Автопроверки: нет прямых обращений в чужую БД; API-изменения аддитивны; контракты актуальны | Нет прямых обращений в чужую БД; аддитивность API |

### Уровень 3. Данные (совместимость с легаси-БД)

| Механизм | Как работает | Что закрывает |
|---|---|---|
| **Anti-Corruption Layer (ACL)** | Транслирует легаси-модель <-> доменную, скрывая "грязные" структуры | Изоляция домена |
| **CDC из легаси (Debezium, log-based)** | Монолит пишет в свои таблицы как раньше; изменения вытягиваются из WAL через Debezium и уходят в Kafka; новый сервис строит свою проекцию. Outbox в легаси не нужен - для своих событий новый сервис использует transactional outbox + релей (Task2/ADR-005) | Переход без изменения кода легаси |
| **Expand-Contract миграции схемы** | Сначала расширяем (новые таблицы/колонки), потом переносим данные, только потом сужаем (удаляем легаси) | Откат миграции без потери данных |
| **CDC-проекция на переходный период** | Новый сервис строит проекцию из потока изменений легаси (Debezium); запись в легаси не дублируется; проекция сверяется с источником | Сверка данных легаси и нового сервиса |
| **Совместимые представления (views)** | Если легаси читает таблицу, которую перенесли, - открываем view/read-model | Отсутствие остановок чтения |

### Уровень 4. Релизы и эксплуатация

| Механизм | Как работает | Что закрывает |
|---|---|---|
| **Feature flags (Unleash)** | Новая логика включается по флагу для сегмента/региона; мгновенный откат | Мгновенный откат; поэтапное включение |
| **Canary / blue-green** | Новый сервис получает малую долю трафика; расхождения сравниваются | Безопасная выкладка новых версий |
| **Параллельное чтение** | Читаем из нового сервиса параллельно с монолитом, сравниваем ответы, не влияя на пользователя | Валидация результатов до переключения |
| **Идемпотентность** | `Idempotency-Key` для платежей/выплат; повтор не создаёт дубль | Защита платежей от дублей |
| **Заголовки трассировки** | Сквозной `correlation-id`/trace-id через Gateway, сервисы и монолит | Сквозная трассировка запросов |

### Карта "механизм -> где виден на C2"

- **API Gateway / BFF** - контейнер в жёлтом слое обратной совместимости.
- **ACL** - там же (трансляция легаси и внешних провайдеров).
- **Schema Registry** - часть шины событий (в описании контейнера и note на диаграмме).
- **CDC/Debezium** - связь `GoFuture Monolith -> шина событий` с подписью "CDC-поток изменений".
- **Feature Flags** - контейнер `Config & Feature Flags` в платформенном boundary.
- **CI/CD** - отдельный boundary (независимый деплой = независимая совместимость).
- **Fallback на монолит** - отражён в описании Gateway и в его note.

### Правила для команд (критерии готовности по совместимости)

1. Ни один релиз не удаляет существующее поле/эндпоинт без прохождения окна деприкейшна.
2. Любое изменение схемы события проходит проверку совместимости в Schema Registry.
3. Каждый межсервисный вызов покрыт consumer-driven контрактом.
4. Переключение чтения/записи на новый сервис - только после сверки (reconciliation) и периода
   параллельное чтение.
5. Все переходные механизмы (CDC-проекция, fallback, view) имеют **срок жизни** и владельца,
   по истечении которого удаляются.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| **Многоуровневый механизм (выбрано)** | Полное покрытие: API, события, данные и релизы | Требует инфраструктуры (Gateway, Registry, CI-гейты) и дисциплины | Принято |
| Обновить всех клиентов принудительно | Не нужно версионирование | Невозможно: старые мобильные приложения в сторах | Отклонено |
| "Big bang"-переключение в один релиз | Проще логически | Простой, критический риск | Отклонено |
| Двойная запись из бизнес-кода монолита | Нет CDC | Двойная запись в коде, расхождения, изменение легаси | Отклонено в пользу log-based CDC |
| Без Schema Registry | Меньше инфраструктуры | Скрытые breaking changes в событиях | Отклонено |

## Недостатки, ограничения и риски

- **Двойная сложность переходного периода** (Gateway+ACL+CDC+views). Цена бесшовности;
  ограничивается сроками волн (ADR-003) и обязательным удалением временных механизмов.
- **CDC создаёт нагрузку** на легаси-БД (logical replication). Митигируется отдельными
  репликами/replication-слотами только для чтения и throttling.
- **Schema Registry и contract-тесты - организационная дисциплина**: без CI-гейтов они
  не работают. Требуется включить их в обязательные проверки пайплайна.
- **Fallback на монолит** может "маскировать" ошибки новых сервисов, если не настроены
  алерты. Правило: каждый fallback - метрика и алерт.
- **Деприкейшн-окно** задерживает "очистку" кода; это осознанный компромисс ради клиентов.

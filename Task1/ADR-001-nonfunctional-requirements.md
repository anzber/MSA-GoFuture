# ADR-001. Нефункциональные требования к целевой архитектуре "GoFuture"

## Общая информация

1. **Родительский артефакт** - описание кейса "GoFuture" (Задание 1, этап 1 "Проработка нефункциональных требований").
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.
4. **Согласующие** - SRE-команда, платформенная команда, команда безопасности, архитектурный комитет.

## Контекст

Монолит "GoFuture" не масштабируется вертикально и вручную. Прежде чем резать его на домены,
нужно зафиксировать измеримые нефункциональные требования (NFR): они определяют границы
сервисов, выбор технологий (gRPC vs REST, Kafka), требования к автоскейлингу, отказоустойчивости,
наблюдаемости и комплаенсу.

## Требования (список NFR)

Для удобства введем отдельные обозначения NFR по группам требований:

| Код группы | English | Группа требований | Что охватывает |
|---|---|---|---|
| `NFR-PE` | Performance Efficiency | Производительность и задержка | latency, пропускная способность, время реакции |
| `NFR-FL` | Flexibility (Scalability) | Масштабируемость и ёмкость | горизонтальное и геораспределённое масштабирование |
| `NFR-RE` | Reliability | Доступность и надёжность | SLO, MTTR, отказоустойчивость, допустимое время простоя, допустимая потеря данных |
| `NFR-FS` | Functional Suitability | Согласованность и данные | строгая и eventual согласованность, идемпотентность, доставка событий, сверка данных |
| `NFR-SE` | Security | Безопасность и комплаенс | регуляторика, платёжные и персональные данные, разграничение доступа, аудит |
| `NFR-MA` | Maintainability (Analysability) | Наблюдаемость | метрики, логи, трейсы, алертинг |
| `NFR-MM` | Maintainability (Modifiability) | Разработка и эксплуатация (DevEx) | time-to-market, независимый деплой, CI/CD, тесты |
| `NFR-CO` | Compatibility | Совместимость | API-версии, вывод API из эксплуатации, старые клиенты, схемы событий |
| `NFR-BC` | Business Constraints | Стоимость | затраты на инфраструктуру, прозрачность затрат |

Бизнес-требования из кейса -> измеримые NFR:

| Бизнес-требование кейса | Раздел NFR |
|---|---|
| 500 тыс. конкурентных поездок | NFR-FL (масштабируемость) |
| Горизонтальное масштабирование в >= 3 регионах | NFR-FL, NFR-RE |
| 99,95 % доступности критичных сервисов | NFR-RE (доступность) |
| Time-to-market <= 2 недель | NFR-MM (DevEx) |
| Локальные регуляторные требования | NFR-SE (безопасность и комплаенс) |
| Динамическое ценообразование в реалтайме | NFR-PE (производительность, события) |
| Умное перераспределение водителей | NFR-PE (latency матчинга), NFR-FS (время ожидания водителя) |
| Интеграция с локальными PSP и картами | NFR-CO (совместимость), NFR-SE |

Легенда приоритета: **К** - критичное (архитектурно значимое), обязательны в первой итерации декомпозиции; **В** - важное, в течение года.

Легенда источника: **кейс** - требование и целевое значение взяты из условия; **кейс, значение - предложение** - цель есть в условии, числовое значение предложено архитектором; **предложение** - сформулировано архитектором, в условии отсутствует.

Столбец "Проверка" - способ верификации требования.

| ID | Требование | Целевое значение | Приоритет | Проверка | Источник |
|---|---|---|---|---|---|
| NFR-RE-01 | Доступность критических сервисов (Booking, Driver, Geography, Pricing, Payments, Payouts) | 99,99 % / год | К | SLO-дашборд | кейс (Задание 3); окно измерения - предложение |

| NFR-RE-03 | MTTR | <= 1 ч | К | постмортемы | кейс |
| NFR-RE-04 | Отсутствие каскадных отказов | отказ одного сервиса не приводит к отказу критического пути | К | chaos-тест | кейс, значение - предложение |
| NFR-RE-05 | Деградация функциональности при отказе зависимости | критический путь не блокируется: проверка Fraud переходит в режим советника (fail-open) с асинхронной до-проверкой; остальные зависимости деградируют без отказа пути | К | chaos-тест | предложение |
| NFR-RE-06 | Допустимое время простоя и потеря данных критических сервисов | отказ зоны: простой секунды-минуты, потеря = 0 (синхронная реплика в зоне); отказ региона: простой секунды-минуты, потеря = 0 (синхронная реплика второго региона юрисдикции); полная потеря юрисдикции - по отдельному согласованию (см. Task3/ADR-004) | К | проверки восстановления | предложение |
| NFR-RE-07 | Допустимое время простоя и потеря данных остальных сервисов | отказ зоны: простой <= 1 ч, потеря = 0 (синхронная реплика) | В | проверки восстановления | предложение |
| NFR-RE-08 | Мультирегиональный failover | автоматический; отказ зоны и региона - без потери подтверждённых данных в БД (RPO БД = 0, синхронная реплика во втором регионе юрисдикции); события шины - в пределах лага зеркалирования; полная потеря юрисдикции - восстановление из копий, по согласованию | К | проверки восстановления | кейс |

> Примечание по доступности: кейс задаёт 99,95 % для критических сервисов, Задание 3 - 99,99 %.
> Принята единая шкала: критические сервисы - 99,99 % (бизнес-минимум 99,95 % тем самым выполнен
> с запасом), остальные - 99,95 %. Трактовка принята как рабочее допущение.
> Окно измерения (год) в кейсе не задано и принято как предложение: годовой бюджет ошибок
> 99,99 % составляет ~52,6 мин/год (месячный эквивалент ~4,4 мин используется только для
> операционного контроля расхода бюджета).

> Примечание по восстановлению (уровни отказа): отказ зоны и отказ региона покрыты синхронной
> репликой между двумя регионами юрисдикции (RPO=0, простой секунды-минуты). Отдельные цели
> аварийного восстановления (простой - часы, потеря данных <= 15 мин) действуют только для
> полной потери юрисдикции целиком - катастрофы, принятой как допущение.

### 9. Стоимость (NFR-BC)

| ID | Требование | Целевое значение | Приоритет | Проверка | Источник |
|---|---|---|---|---|---|
| NFR-BC-01 | Затраты на инфраструктуру | -40 % | В | FinOps-отчёт | кейс |
| NFR-BC-02 | Прозрачность затрат | распределение затрат по сервисам и регионам | В | дашборд | предложение |

> Оговорка по NFR-BC-01: цель "-40 %" задана кейсом и относится к эффекту декомпозиции
> (независимое масштабирование, праворазмер, отказ от избыточных ресурсов монолита).
> Мультирегион (Задание 3) и мультитенантность (Задание 5) **увеличивают** затраты, поэтому
> экономия оценивается качественно и подлежит регулярному пересмотру в FinOps-отчёте;
> часть эффекта достигается после вывода монолита из эксплуатации.
>
> Оценочная модель (порядок величин, требует подтверждения FinOps-пилотом): эффект
> декомпозиции и автоскейлинга ~ -30...40 % на вычислениях и хранении (отказ от избыточного
> вертикального масштабирования); каждый активный регион ~ +20...30 % инфраструктуры
> (постоянная ёмкость и репликация); отдельная БД на крупного тенанта ~ +10...15 % к хранению.
> Итог: цель -40 % достижима для базовой платформы после вывода монолита, но сокращается
> с ростом числа регионов и крупных тенантов.

## Решение

Список NFR принят как **baseline (архитектурно значимые требования)** и используется как
входные данные для всех последующих ADR: он задаёт (а) необходимость доменных границ
с изоляцией данных, (б) событийную платформу, (в) слой обратной совместимости,
(г) мультирегиональное развёртывание, (д) требования к наблюдаемости и CI/CD.

## Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Задать "мягкие" NFR без числовых показателей (например, "высокая доступность") | Невозможно проверить и приоритизировать; не задаёт бюджет инженерных усилий |
| Оставить один общий NFR "99,95 % на всю систему" вместо раздельных показателей по группам сервисов | Финансовые сервисы требуют более жёсткого SLO, чем Notification; единый уровень либо избыточен, либо недостаточен |
| Взять 99,99 % для всех сервисов | Экономически необоснованно: усложняет архитектуру там, где это не нужно бизнесу |

## Недостатки, ограничения и риски

- **Противоречие в источнике** (99,95 % в Задании 1 против 99,99 % в Задании 3) разрешено
  разными показателями для критических и остальных сервисов; при согласовании с бизнесом
  значения могут быть пересмотрены.
- **Стоимость мультирегиона**: NFR-RE-08 / NFR-FL-04 / NFR-SE-01 тянут за собой >= 3 региона
  и data residency - это кратно дороже единого развёртывания; митигируется FinOps
  (NFR-BC-01/NFR-BC-02) и поэтапным расширением регионов (см. ADR-003).
- **SLO 99,99 % зависит от внешних PSP/карт** (NFR-SE-02, NFR-RE-01): недоступность провайдера
  может "съедать" бюджет ошибок - митигируется изоляцией интеграций и исключением внешних
  зависимостей из расчёта SLO сервиса.
- **Часть требований предложена архитектором** (см. столбец "Источник"): числовые значения
  по latency, ёмкости, допустимому времени простоя и потере данных, а также метрики DevEx
  требуют согласования с бизнесом.
- **NFR-дрейф**: требования будут уточняться; для контроля нужен регулярный (ежемесячный)
  пересмотр baseline.

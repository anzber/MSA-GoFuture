# ADR-004. Схема To-Be уровня C2: доменные сервисы и слой обратной совместимости

## Общая информация

1. **Родительский артефакт** - `ADR-002-domain-service-map.md`, `ADR-003-extraction-order.md`.
2. **Артефакты** - [`C2_ToBe_GoFuture.puml`](C2_ToBe_GoFuture.puml), [`C2_ToBe_GoFuture.png`](C2_ToBe_GoFuture.png).
3. **Автор ADR** - Анзор Березгов, архитектор.
4. **Статус** - Принят.

## Контекст

Исходная C2-диаграмма (`source/C2.puml`) описывает монолит: клиенты ходят в `GoFuture Monolith`,
он владеет единственной БД, Celery-воркеры обрабатывают фоновые задачи, а вся инфраструктура
(мониторинг, CI/CD, аналитика) привязана к монолиту. Переход к доменам меняет контейнерный
уровень: появляются независимые сервисы, каждый со своим хранилищем, шина событий и -
самое важное для бесшовной миграции - **слой обратной совместимости**.

Задача этапа - показать целевое состояние C2, в котором:

- домены выделены и владеют своими данными;
- есть механизм, позволяющий старым клиентам и недомигрированным частям монолита продолжать
  работать (обратная совместимость);
- показаны платформенные и инфраструктурные компоненты, обеспечивающие NFR.

## Требования

| No. | Требование |
|---|---|
| 1 | Все 9 доменных сервисов из ADR-002 присутствуют на C2. |
| 2 | Каждый домен владеет своим хранилищем (database-per-service). |
| 3 | На диаграмме виден **механизм обратной совместимости**: Strangler Gateway, ACL, версионирование, реестр схем. |
| 4 | Показать шину событий (Kafka) как основной способ асинхронной интеграции. |
| 5 | Показать легаси-монолит как **выводимый из эксплуатации** (strangler), а не как "якорь". |
| 6 | Показать наблюдаемость и независимый CI/CD как часть целевой архитектуры. |

## Решение

### Что на диаграмме

**Люди:** Пассажир, Водитель, Корпоративный менеджер, Бухгалтер, Оператор поддержки, SRE, Разработчик.

**Клиентские приложения:** пассажирское и водительское приложения (iOS/Android/HMS),
корпоративный портал, админ-панель. Клиенты не знают о внутренней перестройке доменов -
они общаются с единым контрактом Gateway.

**Слой обратной совместимости** (жёлтый на диаграмме):

| Элемент | Роль в совместимости |
|---|---|
| **API Gateway / BFF / Strangler Facade** | Единая точка входа и стабильный внешний REST-контракт. Dual-routing: маршрутизирует запрос либо в новый сервис, либо в остаток монолита. Управляет версиями (`v1..vN`), деприкейшном (`Deprecation`/`Sunset`) и fallback'ом в монолит. |
| **Anti-Corruption Layer (ACL)** | Трансляция моделей "легаси <-> домен" и "внешний провайдер <-> внутренний формат". Изолирует домены от чужеродных моделей и от локальных PSP/карт по регионам. |

**Платформенные сервисы:** Identity & Access (OIDC/Keycloak), Config & Feature Flags (Unleash),
шина событий (Kafka + Schema Registry, партиционирование по регионам).

**Доменные сервисы:** Booking, Driver, Geography, Pricing, Payments, Payouts, Notification,
Analytics, Fraud - каждый со своим хранилищем (Booking DB, Driver DB, Geo Index, Pricing DB+Cache,
Журнал операций Payments, Журнал операций Payouts, Notification DB, Analytics DW, Fraud DB).

**Легаси (красным пунктиром):** GoFuture Monolith и Legacy DB - присутствуют, пока идёт
декомпозиция; уменьшаются по волнам и удаляются в волне 5.

**Внешние и локальные сервисы:** Яндекс Пэй, локальные PSP, Яндекс Карты, локальные карты,
FCM/APNS/HMS, банковские API - все доступны только через ACL.

**Наблюдаемость и CI/CD:** OpenTelemetry Collector -> Prometheus/Grafana + Loki/Jaeger;
независимый деплой сервисов (система контроля версий (Git), Jenkins, Docker Registry,
Docker-based deployment, Terraform/IaC).

### Как именно обеспечивается обратная совместимость (на схеме и за её пределами)

1. **Strangler Facade.** Gateway публикует те же URL, что и монолит. Пока домен не выделен,
   запрос идёт в монолит; после выделения - в сервис. Для клиента ничего не меняется.
2. **Версионирование и деприкейшн.** Новые сервисы публикуют API с версией; старые версии
   живут >= 2 релиза / 90 дней (NFR-CO-02). BFF скрывает перестройку от мобильных приложений,
   которые нельзя обновить мгновенно (NFR-CO-03).
3. **ACL.** Переводит легаси-модель и внешние форматы в доменные и обратно, не "протекая"
   чужеродной моделью внутрь домена.
4. **Шина событий + Schema Registry.** События имеют envelope
   `{eventType, version, region, occurredAt, payload}`; совместимость схем -
   `BACKWARD_TRANSITIVE` (NFR-CO-04), потребители игнорируют неизвестные поля.
5. **CDC (Debezium, log-based) + outbox новых сервисов.** Монолит отдаёт изменения своей БД
   в Kafka через Debezium (чтение WAL, без изменения легаси-кода); новые сервисы публикуют
   свои события через transactional outbox (детали - ADR-005/ADR-006).

### Выбор технологий и логика

| Решение | Обоснование (связь с NFR) |
|---|---|
| Gateway + BFF (Kong/Envoy) | Единый контракт, rate limiting/WAF, strangler-маршрутизация (NFR-CO-01), независимый деплой (NFR-MM-02) |
| gRPC между доменами для критичных Query | Низкая latency матчинга (NFR-PE-04), строгие контракты |
| Kafka как шина событий | 500 тыс. поездок (NFR-FL-01), realtime-ценообразование (NFR-PE-05), развязка доменов (NFR-FS-02) |
| Database-per-service | Изоляция отказов (NFR-RE-04), независимое масштабирование (NFR-FL-03), владение данными (см. ADR-002) |
| OTel + Prometheus/Grafana + Loki/Jaeger | 100 % наблюдаемость (NFR-MA-01, NFR-MA-02), SLO-based алертинг (NFR-MA-03) |
| Keycloak/OIDC | Единый SSO/RBAC (NFR-SE-04), доступ корпоративных клиентов и админов |
| Git + Jenkins + Docker Registry + Docker-based deployment, IaC | Time-to-market <= 2 недель (NFR-MM-01), пайплайн <= 15 мин (NFR-MM-03), инфраструктура как код (NFR-MM-07) |


### Выбор языка реализации сервисов

В C2 у большинства сервисов указан Go, у Fraud - Python/Go. Обоснование и компромисс:

- **Почему Go:** критические сервисы (Booking, Driver, Geography, Pricing, Payments, Payouts)
  работают под высокой нагрузкой и с жёсткими требованиями к задержке (NFR-PE). Go даёт
  предсказуемую задержку, низкое потребление памяти и удобную конкурентность, что важно при
  500 тыс. конкурентных поездок.
- **Почему не всё на Go:** текущий лендскейп команды - Python/Django. Fraud (ML), Analytics и
  Notification исторически на Python, и там важнее экосистема (ML, обработка данных), а не
  микросекунды. Массовый перевод всего на Go ударил бы по time-to-market (NFR-MM-01) из-за
  переобучения команды.
- **Решение:** Go - для latency-критичных доменов и высоконагруженных уведомлений; Python
  сохраняется для Fraud (ML) и Analytics. Переход постепенный, по волнам (см. ADR-003),
  с обучением команды.
- **Риски:** нехватка компетенций Go, стоимость обучения и найма, риск срыва сроков. Митигация:
  пилот на одном сервисе, парное программирование, единый шаблон сервиса.
- **Альтернатива:** оставить Python для большинства сервисов - проще для команды, но выше риск
  не уложиться в требования по задержке и потреблению ресурсов под пиковой нагрузкой.

### Как читать диаграмму и как её пересобрать

На отрисовке 
- **жёлтым** - слой обратной совместимости, 
- **красным пунктиром** - легаси,
- **синим** - целевые домены/платформа.


## Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Без Gateway: клиенты ходят напрямую в сервисы | Невозможна бесшовная миграция (нет точки strangler), сложны версионирование и WAF |
| "Общая шина"/ESB вместо Gateway + Kafka | Возврат к централизованной логике и "умной трубе"; противоречит автономии доменов |
| Общая БД на переходный период без CDC | Требует "двойной записи" из кода монолита; риск расхождений и блокирующих изменений |
| Не показывать монолит на To-Be (сразу "убрать") | Не соответствует реальности миграции; ревьюер не увидит механизм совместимости |
| Отдельный BFF для каждого клиента с нуля | Больше кода и дублирования; на старте достаточно одного Gateway + BFF-слоя |

## Недостатки, ограничения и риски

- **Gateway - критический компонент:** его недоступность = недоступность всего (NFR-RE-01).
  Митигируется кластером в каждом регионе, health-checks, статическим fallback-конфигом.
- **Переходный период сложнее целевого состояния:** одновременно живут монолит, сервисы и
  ACL. Это осознанная плата за отсутствие простоя; длительность ограничена волнами ADR-003.
- **ACL может стать "божественным" компонентом**, если сложить туда всю логику трансляции.
  Правило: ACL - тонкий адаптер, без бизнес-логики.
- **Распределённые данные:** database-per-service вводит eventual consistency (NFR-FS-02), что
  повышает требования к Saga, outbox и reconciliation (Task1/ADR-006).

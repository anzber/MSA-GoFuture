# ADR-001 (Task4). Пайплайн данных: сбор, обработка, ML и BI

## Общая информация

1. **Родительский артефакт** - `Task2/ADR-001..ADR-005` (события, топики, потребители, доставка),
   `Task3/ADR-002` (репликация), лендскейп кейса (Spark/Flink, ClickHouse, DataLens).
2. **Артефакт** - [`C4_DataPipeline.puml`](C4_DataPipeline.puml) / `.png`.
3. **Автор ADR** - Анзор Березгов, архитектор.
4. **Статус** - Принят.

## Контекст

Данные нужны трём большим потребителям: ML-моделям (динамическое ценообразование, прогноз
спроса, фрод), BI-инструментам (отчёты и дашборды) и аналитике реального времени. Данные
порождаются всеми микросервисами. Нужен единый пайплайн: от источника до ML и BI, без ручных
выгрузок и без прямых запросов в БД чужих сервисов.

## Требования

| No. | Требование |
|---|---|
| 1 | Сбор данных из всех микросервисов единообразно. |
| 2 | Обработка в реальном времени (для цен, спроса, фрода) и пакетная (для витрин). |
| 3 | Интеграция с ML-платформой (обучение и инференс моделей). |
| 4 | Интеграция с BI-инструментами (дашборды и отчёты). |
| 5 | Данные обезличены там, где это требуется локальными правилами (Task3). |
| 6 | Качество данных контролируется (см. ADR-002). |

## Решение

### Этапы пайплайна

| Этап | Что происходит | Инструменты |
|---|---|---|
| 1. Сбор | сервисы пишут события в outbox; CDC публикует их в шину событий | Kafka, CDC (Debezium) |
| 2. Транспорт | единый поток доменных событий по регионам | Kafka, Schema Registry |
| 3. Потоковая обработка | нормализация, обогащение, агрегаты и признаки в реальном времени | Flink |
| 4. Пакетная обработка | витрины, исторические признаки, пересчёты | Spark, Airflow |
| 5. Хранение | "сырые" данные и большие объёмы; быстрые витрины | озеро данных (объектное хранилище), ClickHouse |
| 6. ML-платформа | витрина признаков, обучение, реестр моделей, онлайн-инференс | ML-платформа (внутренняя) |
| 7. BI | дашборды и отчёты поверх витрин | DataLens |
| 8. Возврат в продукт | результаты моделей влияют на цены, матчинг, фрод | доменные сервисы |

### Поток данных

```
Микросервисы -> outbox -> CDC -> Kafka (шина событий)
   Kafka -> Flink (реальное время) -> ClickHouse (витрины реального времени)
   Kafka -> озеро данных (сырые данные) -> Spark + Airflow (пакет) -> ClickHouse (витрины), витрина признаков
   витрина признаков -> ML-платформа: обучение -> реестр моделей -> онлайн-инференс -> доменные сервисы
   ClickHouse -> DataLens (BI-дашборды)
   Kafka -> проверки качества данных -> зона отбраковки (см. ADR-002)
```

### Интеграция с ML-платформой

- **Витрина признаков**: единое место расчёта и хранения признаков (спрос, загрузка водителей,
  история цен, поведение пользователя), чтобы модели не считали признаки по-своему.
- **Обучение моделей**: пакетно (Spark + Airflow) на исторических данных; результат - модель,
  зарегистрированная в реестре моделей.
- **Онлайн-инференс**: сервисы вызывают модель синхронно (например, расчёт цены) или получают
  результат через события (например, оценка фрода).
- Модели динамического ценообразования, прогноза спроса и обнаружения фрода используют общую
  витрину признаков.

### Интеграция с BI

- DataLens подключается к витринам ClickHouse.
- Отчёты: загрузка водителей, спрос по зонам, обороты и выплаты, конверсия, фрод-инциденты.
- Для BI используются обезличенные данные (без персональных данных), чтобы не нарушать
  локальные требования (Task3).

### Регионы и обезличивание

- Данные собираются в каждом регионе; для общей аналитики выносятся **только обезличенные
  агрегаты** (см. Task3/ADR-002).
- Персональные данные остаются в домашнем регионе; соблюдение обеспечивается механизмами
  residency (теги региона, политики хранилища, проверки в CI - см. Task3/ADR-002).
- ML-модели обучаются на обезличенных признаках; агрегаты публикуются с порогом k-anonymity
  (см. Task3/ADR-002).

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Событийный сбор + поток + пакет (выбрано) | единый источник, realtime + история | два стека обработки | Принято |
| Прямые запросы в БД сервисов | простота | связность, нагрузка на прод, нет единой истории | Отклонено |
| Только пакетная обработка | проще | нет realtime (цены, фрод) | Отклонено |
| Только потоковая обработка | быстро | дорого для больших исторических пересчётов | Частично (realtime-витрины) |
| Готовый облачный ETL-сервис | быстрый старт | вендор-лок, данные вне периметра | Отклонено |

## Недостатки, ограничения и риски

- **Задержка и согласованность**: данные в BI приходят с задержкой (пакетно); realtime-витрины -
  быстрее, но неполные.
- **Дублирование данных** между озером и ClickHouse; нужно управлять жизненным циклом.
- **Стоимость** хранения и обработки больших объёмов; митигируется политиками хранения и
  автоскейлингом.
- **Качество данных** критично для ML: без проверок модели учатся на "мусоре" (см. ADR-002).
- **Обезличивание** может снизить точность моделей; это осознанный компромисс ради комплаенса.

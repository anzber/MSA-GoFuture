# ADR-002 (Task4). Механизмы обеспечения качества данных

## Общая информация

1. **Родительский артефакт** - `ADR-001-data-pipeline.md`, `Task2/ADR-001` (схемы событий),
   теория (качество данных, проверки, профилирование).
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.

## Контекст

ML-модели и BI-отчёты строятся на данных из многих источников. Если данные неполные,
устаревшие, дублируются или приходят в неверной структуре, модели дают неверные цены и
прогнозы, а отчёты вводят бизнес в заблуждение. Качество данных нужно обеспечивать не в конце,
а на всём пути: от источника до витрины.

## Требования

| No. | Требование |
|---|---|
| 1 | Данные соответствуют согласованной структуре (схеме). |
| 2 | Выявляются неполные, дублирующиеся и некорректные записи. |
| 3 | "Плохие" данные не попадают в витрины и модели, но не теряются бесследно. |
| 4 | Известно происхождение данных (откуда пришли и как преобразованы). |
| 5 | Качество данных измеряется и контролируется метриками. |
| 6 | Персональные данные обезличиваются. |

## Решение

### 1. Контракты и схемы

- Схемы событий и таблиц регистрируются в Schema Registry; изменения только аддитивные
  (см. Task2/ADR-001).
- Контракты между источниками и потребителями проверяются автоматически в конвейере: запись,
  не соответствующая схеме, не проходит дальше.

### 2. Проверки качества на каждом этапе

Проверки выполняются на входе (события), после потоковой обработки и перед загрузкой в витрины:

| Тип проверки | Что проверяем |
|---|---|
| Полнота | обязательные поля заполнены, нет пропусков |
| Уникальность | нет дублирующихся записей (по идентификатору) |
| Допустимые значения | значения в ожидаемых диапазонах (цена > 0, координаты в границах) |
| Ссылочная целостность | ссылки на существующие сущности (водитель, поездка) |
| Своевременность | данные не старше допустимого времени |
| Согласованность | агрегаты совпадают с источниками |

### 3. Идемпотентность и дедупликация

- Повторная доставка событий не создаёт дублей в витринах (дедупликация по идентификатору
  события, см. Task2/ADR-005).
- Пересчёты витрин идемпотентны: повторный запуск даёт тот же результат.

### 4. Зона отбраковки

- Записи, не прошедшие проверки, не удаляются и не попадают в витрины, а помещаются в
  **зону отбраковки** с причиной.
- Дежурный или команда-владелец разбирает такие записи; после исправления их можно перезапустить
  в конвейер.

### 5. Происхождение данных

- Для каждой витрины фиксируется, из каких источников и какими преобразованиями она получена
  (происхождение данных).
- Это позволяет разобраться, откуда взялось сомнительное значение, и повторить расчёт.

### 6. Каталог и владельцы

- Ведётся реестр наборов данных: владелец, назначение, схема, периодичность обновления.
- Владелец отвечает за качество своего набора данных.

### 7. Мониторинг и метрики качества

| Метрика | Что показывает |
|---|---|
| доля записей, прошедших проверки | общее качество потока |
| число записей в зоне отбраковки | объём проблемных данных |
| задержка обновления витрин | своевременность |
| расхождение с источником при сверке | согласованность |
| доля пропусков по обязательным полям | полнота |

На метрики настроены алерты: при ухудшении качества данных дежурный получает сигнал.

### 8. Сверка с источником

- Периодическая сверка витрин с исходными данными по контрольным суммам и количеству записей.
- Расхождение выше порога - сигнал остановить публикацию данных в ML и BI до выяснения.

### 9. Версионирование и воспроизводимость

- Версионируются схемы данных и модели; обучение модели можно воспроизвести на конкретной
  версии данных.
- Витрины строятся так, чтобы из "сырых" данных можно было пересобрать результат.

### 10. Обезличивание

- Персональные данные обезличиваются до попадания в общий аналитический слой (см. Task3).
- В витрины и BI попадают только агрегаты без персональных данных.

### Слои данных

Конвейер строит три слоя: **сырой** (как пришло), **очищенный** (прошёл проверки и нормализацию),
**витрины** (готовые для ML и BI). Качество повышается от слоя к слою.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Проверки на всех слоях (выбрано) | раннее выявление проблем, доверие к данным | задержка и стоимость проверок | Принято |
| Проверки только перед витриной | меньше проверок | "грязные" данные проходят дальше и дороже чистятся | Отклонено |
| Без автоматических проверок, только вручную | дешевле на старте | ошибки находят поздно, модели учатся на мусоре | Отклонено |
| Строгий запрет любых отклонений (всё или ничего) | максимальная чистота | один сбой блокирует весь поток | Отклонено (используем зону отбраковки) |

## Недостатки, ограничения и риски

- **Задержка** из-за проверок в конвейере; баланс между скоростью и качеством настраивается
  порогами.
- **Зона отбраковки требует сопровождения**: без разбора проблемные записи накапливаются.
- **Стоимость проверок и хранения слоёв**; управляется политиками хранения и приоритетом проверок.
- **Обезличивание снижает детализацию** и может ухудшить качество моделей - осознанный компромисс.
- **Человеческий фактор**: качество держится на владельцах данных и дисциплине контрактов.

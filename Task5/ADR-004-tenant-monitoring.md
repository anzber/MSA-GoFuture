# ADR-004 (Task5). Мониторинг мультитенантного окружения

## Общая информация

1. **Родительский артефакт** - `ADR-001-tenant-isolation.md`, `ADR-002-iam-sso.md`;
   инструменты мониторинга из лендскейпа и Task2.
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.

## Контекст

На одной платформе работает много тенантов (партнёров). Нужно видеть состояние каждого тенанта
отдельно: его нагрузку, ошибки, качество обслуживания и использование ресурсов. Иначе один
"шумный" тенант ухудшит работу остальных, а проблемы конкретного партнёра останутся незамеченными.

## Требования

| No. | Требование |
|---|---|
| 1 | Метрики и алерты в разрезе каждого тенанта. |
| 2 | Контроль "шумного соседа" через квоты и лимиты. |
| 3 | Цели по качеству (SLO) для каждого тенанта. |
| 4 | Сводная картина по всем тенантам для платформы. |
| 5 | Аудит доступа и действий в разрезе тенанта. |

## Решение

### Единый мониторинг с разбивкой по тенантам

Используется существующий слой (OpenTelemetry Collector, Prometheus, Grafana, Loki, Jaeger,
Alertmanager - см. Task2) с обязательной меткой `tenantId` во всех метриках, логах и трейсах.

| Уровень | Что показываем |
|---|---|
| Тенант | нагрузка, задержка, ошибки, использование квот, объём данных, стоимость |
| Платформа | суммарная нагрузка, здоровье общих компонентов, распределение ресурсов |
| Сводный | рейтинг "здоровья" тенантов, тенанты с риском нарушения целей |

### Метрики по тенанту

| Метрика | Что показывает |
|---|---|
| число запросов в секунду | нагрузка тенанта |
| задержка (p95) | качество обслуживания пользователей тенанта |
| доля ошибок | стабильность |
| использование квоты (CPU, память, диск) | приближение к лимиту, риск "шумного соседа" |
| отставание обработки событий | своевременность |
| объём данных и рост | планирование ёмкости и стоимость |
| доступность (SLO) | выполнение целей по тенанту |
| события безопасности тенанта | аудит и инциденты |

### Изоляция ресурсов и квоты

- Для каждого тенанта задаются **квоты и лимиты** (запросы, ресурсы, объём данных).
- При приближении к лимиту - предупреждение владельцу тенанта, затем ограничение.
- Так один тенант не может перегрузить общие сервисы и повлиять на других.

### Алерты и цели

- Алерты настраиваются **на тенанта**: нарушение целей, рост ошибок, исчерпание квот,
  подозрительная активность.
- Цели (SLO) задаются и отслеживаются по каждому тенанту; на выгорание целей - предупреждение.
- Сводный алерт - если растёт число "нездоровых" тенантов или общий ресурс на пределе.

### Аудит

- Действия пользователей и интеграций тенанта попадают в аудит с меткой тенанта.
- Владелец тенанта видит аудит своего тенанта; платформа - сводно.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Единый мониторинг с разбивкой по тенантам (выбрано) | единая картина + детали по тенанту | высокая "кардинальность" метрик | Принято |
| Отдельный мониторинг на каждого тенанта | полная изоляция | дублирование, сложно поддерживать | Отклонено |
| Общий мониторинг без разбивки | простота | проблемы тенанта не видны, нет контроля соседей | Отклонено |
| Облачный сервис мониторинга на тенанта | быстрый старт | стоимость и данные вне периметра | Отклонено |

## Недостатки, ограничения и риски

- **Высокая кардинальность метрик** (много тенантов x много метрик) удорожает хранение;
  митигируется агрегатами, выборкой и разумными метками.
- **Настройка квот** - компромисс между защитой соседей и свободой тенанта; значения
  пересматриваются по факту использования.
- **Рост числа тенантов** усложняет дашборды; помогает сводный рейтинг здоровья и авто-группировка.
- **Стоимость** хранения логов и трейсов по тенантам; управляется политиками хранения.

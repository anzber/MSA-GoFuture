# ADR-003 (Task5). Автоматизированный онбординг партнёров

## Общая информация

1. **Родительский артефакт** - `ADR-001-tenant-isolation.md`, `ADR-002-iam-sso.md`,
   условие Задания 5 (онбординг).
2. **Артефакт** - [`Onboarding_Flow.puml`](Onboarding_Flow.puml) / `.png`.
3. **Автор ADR** - Анзор Березгов, архитектор.
4. **Статус** - Принят.

## Контекст

"GoFuture" хочет быстро запускать партнёров в новых регионах. Ручное подключение (создание
базы, настройка доступа, интеграций) медленное и подвержено ошибкам. Нужен автоматизированный
процесс онбординга: от заявки до работающего изолированного тенанта с проверками изоляции.

## Требования

| No. | Требование |
|---|---|
| 1 | Подключение нового партнёра за короткое время без ручных операций. |
| 2 | Полная изоляция данных нового тенанта (см. ADR-001). |
| 3 | Автоматическая настройка доступа (роли, SSO, ключи). |
| 4 | Подключение локальных платёжных и картографических сервисов. |
| 5 | Автоматические проверки изоляции и работоспособности до активации. |
| 6 | Мониторинг тенанта с момента активации. |

## Решение

### Этапы онбординга (автоматизированные)

| Шаг | Что происходит | Автоматизация |
|---|---|---|
| 1. Заявка | партнёр заполняет заявку и данные | портал онбординга |
| 2. Тенант | создаётся запись тенанта, выбирается регион | сервис тенантов |
| 3. Выделение ресурсов | создаётся отдельная БД тенанта (или отдельный инстанс по триггеру), роли СУБД, ключ шифрования, лимиты | оркестратор выделения ресурсов (шаблоны инфраструктуры как кода) |
| 4. Конфигурация | тарифы, зоны, флаги функций | сервис конфигурации |
| 5. Доступ | администратор тенанта, роли, SSO, ключи API | IAM (см. ADR-002) |
| 6. Интеграции | локальные платёжные, картографические, push-сервисы | каталог интеграций |
| 7. Данные | импорт справочников (парк, водители, зоны) | конвейер импорта |
| 8. Проверки | тесты изоляции, smoke-тесты, проверки данных | слой проверок |
| 9. Активация | включение в маршрутизацию и шину событий | оркестратор выделения ресурсов |
| 10. Мониторинг | дашборд и алерты по тенанту | слой мониторинга (см. ADR-004) |

### Принципы

- Онбординг - **конвейер с шагами и статусами**; каждый шаг идемпотентен и повторяем.
- Если проверки не пройдены, тенант **не активируется**, а процесс откатывается.
- Выделение ресурсов выполняется по **шаблонам** (инфраструктура как код), поэтому все тенанты
  настроены одинаково и изолированы.
- Партнёр видит статус онбординга в портале.

### Проверки перед активацией

- Тест изоляции: тенант не видит данные других тенантов.
- Тест доступа: роли видят только свои данные.
- Smoke-тесты: базовые сценарии поездки и оплаты.
- Проверки данных: справочники импортированы, обязательные поля заполнены.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Автоматизированный конвейер онбординга (выбрано) | быстро и одинаково для всех | сложно построить | Принято |
| Ручное подключение | просто на старте | медленно, ошибки, не масштабируется | Отклонено |
| Полностью самостоятельный онбординг без проверок | очень быстро | риск неверной изоляции и данных | Отклонено |
| Отдельный проект под каждого партнёра | гибко | дорого и долго | Отклонено |

## Недостатки, ограничения и риски

- **Сложность выделения ресурсов**: ошибка в шаблонах отражается на всех тенантах; нужны ревью
  шаблонов и проверки.
- **Откат онбординга**: не все шаги просто откатить (созданные интеграции, импортированные
  данные); процесс предусматривает безопасное удаление тенанта.
- **Скорость проверок**: полный набор тестов занимает время; часть проверок запускается
  параллельно.
- **Зависимость от внешних партнёров**: подключение локальных платёжных и картографических
  сервисов может задерживаться по причинам вне платформы.

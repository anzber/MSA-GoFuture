# ADR-001 (Task5). Модель изоляции данных между партнёрами

## Общая информация

1. **Родительский артефакт** - условие Задания 5, `Task3/ADR-005-compliance.md` (локальные
   требования).
2. **Автор ADR** - Анзор Березгов, архитектор.
3. **Статус** - Принят.

## Контекст

Платформа обслуживает несколько партнёров (тенантов): локальные службы такси, банки, e-commerce.
Партнёры требуют **полной изоляции данных** (данные одного партнёра не должны быть видны другому)
и **кастомизации** (свои тарифы, зоны, способы оплаты). Изоляция должна быть не только логической,
но и защищена на уровне хранения и доступа.

## Требования

| No. | Требование |
|---|---|
| 1 | Данные одного тенанта недоступны другим тенантам. |
| 2 | Возможна кастомизация поведения под тенанта без изменения общего кода. |
| 3 | Тенант можно подключить быстро (см. ADR-003). |
| 4 | Изоляция выдерживает проверку (тесты изоляции). |
| 5 | Учитываются локальные требования к хранению данных (регион тенанта). |

## Варианты изоляции

| Модель | Изоляция | Стоимость | Когда применяем |
|---|---|---|---|
| Общая БД, у каждой строки идентификатор тенанта | слабая (риск ошибки в запросе) | минимальная | не используем как основную |
| Схема на тенанта в общей БД + отдельные роли СУБД | средняя: разделение по схемам и правам | средняя | **исключение** для очень мелких тенантов |
| **Отдельная БД на тенанта** | высокая: своё хранилище и отдельная роль СУБД | выше | **по умолчанию** |
| Отдельный экземпляр/кластер на тенанта | максимальная | максимальная | регулируемые и особо крупные (по триггеру) |

> RLS (построчная защита по идентификатору тенанта) применима только к модели "общая БД со
> строковым дискриминатором тенанта" (не выбрана) и в дефолтной модели не используется.

## Решение

**Модель изоляции:**

- **По умолчанию** - **отдельная база данных на тенанта** в его регионе, с отдельной ролью и
  учётными данными СУБД. Это физическое разделение хранилища: данные тенантов лежат в разных БД,
  а кросс-тенантные запросы невозможны по построению.
- **Регулируемые и особо крупные тенанты** - отдельный **экземпляр/кластер** (обязательно по
  триггеру, а не по желанию).
- **Исключение** - для очень мелких тенантов допускается **схема на тенанта** в общей БД
  (с отдельной ролью); при росте объёма или появлении требований тенант переводится на отдельную БД.
- **Шифрование на тенанта** - данные шифруются отдельным ключом (envelope-encryption, ключ в KMS
  на тенанта) как дополнительный барьер поверх разделения.
- **Общие данные** (справочники платформы, каталог) хранятся отдельно и доступны только на чтение.

### Правила изоляции

1. Любая запись и запрос выполняются **в контексте тенанта**; идентификатор тенанта передаётся
   от шлюза и не может быть подменён клиентом.
2. Запросы к данным разных тенантов в одном запросе **запрещены**; для аналитики используются
   только обезличенные агрегаты.
3. Изоляция обеспечивается на уровне СУБД: **отдельная БД (или схема)** и **отдельная
   роль/учётные данные** на тенанта, плюс шифрование данных отдельным ключом (KMS на тенанта) -
   а не только проверкой в коде приложения.
4. Для каждого тенанта задаётся **регион хранения** (по локальным требованиям, см. Task3).
5. Ключи доступа и секреты тенанта хранятся отдельно (см. ADR-002).
6. Ведётся журнал доступа к данным тенанта.

### Почему это закрывает требование "полной изоляции"

**Определение.** По умолчанию применяется **физическое разделение**: отдельная база данных на
тенанта. Это прямо отвечает буквальному требованию "полной изоляции данных между партнёрами".
Логическая изоляция (схема на тенанта) остаётся только исключением для очень мелких тенантов.

**Триггер перевода на отдельный экземпляр/кластер** (обязательно, а не опция) - если выполнено
хотя бы одно:

- регуляторное требование страны или отрасли о физическом разделении;
- прямое условие контракта с партнёром;
- объём данных или нагрузка выше установленного порога.

**Шифрование на тенанта** (отдельный ключ в KMS) - дополнительный барьер поверх разделения;
оно не заменяет физическое разделение, а усиливает его.

### Кастомизация

- Конфигурация и флаги функций на тенанта: тарифы, зоны, способы оплаты, правила матчинга.
- Общий код обслуживает всех; различия задаются конфигурацией, а не отдельными сборками.
- Особые требования, не покрываемые конфигурацией, реализуются как расширения без влияния
  на других тенантов.

### Регион и локальные требования

- Тенант привязывается к региону (Task3); его данные хранятся в этом регионе.
- **Развёртывание по регионам:** отдельная БД (или схема) тенанта создаётся **в регионе тенанта**
  (residency, NFR-SE-01) - не один общий кластер на все страны.
- Между регионами данные тенанта не реплицируются; наружу идут только обезличенные агрегаты.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Отдельная БД на тенанта по умолчанию + отдельный инстанс для регулируемых (выбрано) | физическая изоляция, проще комплаенс, per-tenant restore | дороже в эксплуатации при большом числе тенантов | Принято |
| Схема на тенанта по умолчанию | дешевле при тысячах мелких тенантов | изоляция логическая, может не удовлетворить "полную изоляцию" | Отклонено (оставлено исключением для мелких) |
| Только идентификатор тенанта в общей БД | дешевле всего | слабая изоляция, риск утечки при ошибке в запросе | Отклонено |
| Сразу отдельный экземпляр на всех | максимальная изоляция | избыточно дорого | Отклонено |

## Недостатки, ограничения и риски

- **Стоимость и эксплуатация**: N баз - это N резервных копий, миграций, мониторинга; требует
  автоматизации выделения (см. ADR-003).
- **"Шумный сосед" на уровне инстанса**: несколько БД в одном инстансе делят ресурсы; нужны
  квоты и лимиты (см. ADR-004).
- **Рост числа БД/инстансов**: нужны учёт, лимиты кластера и планирование ёмкости.
- **Риск ошибки в конфигурации изоляции**: обязательны автоматические тесты изоляции при
  подключении каждого тенанта (см. ADR-003).

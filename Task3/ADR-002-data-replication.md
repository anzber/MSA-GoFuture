# ADR-002 (Task3). Схема репликации данных между регионами

## Общая информация

1. **Родительский артефакт** - `ADR-001-region-selection.md`, `Task1/ADR-006-data-migration.md`,
   теория (репликация, CDC, зеркалирование топиков).
2. **Артефакт** - [`Replication.puml`](Replication.puml) / `.png` (изменения красным).
3. **Автор ADR** - Анзор Березгов, архитектор.
4. **Статус** - Принят.

## Контекст

Регионы работают одновременно, но персональные данные резидентов не должны покидать их страну.
Значит, репликация не может быть "всё во все регионы": нужно разделить данные по классам и
для каждого выбрать способ и направление репликации.

## Требования

| No. | Требование |
|---|---|
| 1 | Персональные данные хранятся в домашней юрисдикции: синхронно реплицируются между двумя её регионами, но не покидают страну. |
| 2 | Справочные данные одинаковы во всех регионах. |
| 3 | Обезличенная аналитика доступна централизованно. |
| 4 | Репликация не должна блокировать основной поток операций. |
| 5 | Отказ региона не должен приводить к потере подтверждённых данных. |

## Классы данных и способ репликации

| Класс данных | Где хранится | Между регионами | Механизм |
|---|---|---|---|
| Персональные данные (профили, поездки, платежи) | в домашней юрисдикции (два региона) | между юрисдикциями - не реплицируется; внутри юрисдикции - синхронно между двумя регионами | синхронная репликация между регионами юрисдикции |
| Справочные данные (тарифы, конфигурация, каталог партнёров, правила) | у владельца + реплики | реплицируется во все регионы (асинхронно, в одну сторону) | логическая репликация и CDC |
| Обезличенные агрегаты и аналитика | региональное аналитическое хранилище + общий слой | в общий аналитический слой (асинхронно) | поток событий и CDC |
| Глобальные сервисы (идентификация, каталог, конфигурация) | во всех регионах | реплики во все регионы | собственная репликация сервиса |

Принцип: **у справочных данных один владелец-регион** (запись только там), остальные регионы
получают реплики только для чтения. Так не возникает конфликтов между регионами.

### Почему общий слой не нарушает локальное хранение

Мастер справочных данных и общий аналитический слой **не содержат персональных данных**
(только справочники и обезличенные агрегаты), поэтому их размещение вне домашнего региона
пользователя не нарушает требования. Глобальный IAM хранит только **неперсональные
идентификаторы и учётные данные** (идентификатор пользователя, роли, сессии); персональные
атрибуты (телефон, e-mail) остаются в домашней юрисдикции и в глобальный слой не реплицируются.

Для устойчивости мастер и Schema Registry разворачиваются
отказоустойчиво (несколько экземпляров минимум в двух зонах, автоматический failover,
резервные копии с RPO/RTO уровня платформы). При недоступности мастера регионы продолжают
работу на репликах справочных данных только для чтения (см. Task2/ADR-002).

### Принудительное соблюдение residency

Декларации "персональные данные не реплицируются" недостаточно - нужен механизм:

1. **Тег региона у данных**: каждая запись с персональными данными помечается домашним
   регионом и хранится только в нём.
2. **Политики хранилища/СУБД**: доступ и запись ограничены домашним регионом; попытка записи
   персональных данных в чужой регион запрещена на уровне прав и региональных политик.
3. **Сервисный слой**: операции с персональными данными разрешены только в домашнем регионе
   (проверка по токену, см. ADR-003); межрегиональный прокси обслуживает только публичные
   и некритичные операции.
4. **Проверка в CI (fitness-function)**: статическая проверка, что модели и топики с
   персональными данными не участвуют в межрегиональной репликации; тесты изоляции при
   каждом релизе.
5. **Аудит**: журналирование и алерты по попыткам обращения к персональным данным вне
   домашнего региона.

## Репликация по хранилищам

| Хранилище | Внутри региона | Между регионами |
|---|---|---|
| PostgreSQL (данные сервисов) | синхронная реплика между зонами и между двумя регионами юрисдикции | логическая репликация справочных данных; CDC для агрегатов |
| Kafka | кластеры в обоих регионах юрисдикции | **внутри юрисдикции** - одностороннее зеркалирование бизнес-топиков primary -> standby (MirrorMaker 2, `IdentityReplicationPolicy`, sync offsets); между юрисдикциями - только справочные и агрегатные |
| ClickHouse (аналитика) | реплика внутри региона | сбор обезличенных агрегатов в общий слой |
| Redis (кэш) | регион-локальный | не реплицируется |
| Объектное хранилище (образы, артефакты, выгрузки) | на регион | репликация артефактов и общих образов |

## Модель согласованности

- Основной поток операций (поездка, оплата) - **строгая согласованность внутри региона**.
- **Между юрисдикциями** репликация **асинхронная**: справочные данные и обезличенные агрегаты
  приходят с задержкой (секунды).
- **Внутри юрисдикции персональные данные реплицируются синхронно** между двумя её регионами
  (см. ADR-001 и раздел ниже); их "одно место" - это юрисдикция из двух регионов.
- Обезличенные агрегаты формируются с порогом **k-anonymity** (например, k >= 10): агрегаты
  по малым группам не публикуются, что исключает ре-идентификацию; персональные идентификаторы
  в общий слой не попадают.

## Согласованность и отказ региона

- Персональные данные юрисдикции синхронно реплицируются между **двумя регионами развёртывания
  внутри страны** (см. ADR-001) и между зонами внутри региона. Поэтому отказ зоны или одного
  региона не приводит к потере подтверждённых данных (**RPO БД = 0**), а простой ограничен
  секундами-минутами (промоушен реплики, реконнекты клиентов, переключение трафика).
- **Резервное копирование:** помимо синхронных реплик, данные непрерывно архивируются
  (WAL и снапшоты) в защищённое хранилище **в той же стране** (требование локального хранения).
  Синхронная реплика закрывает отказ зоны и региона; на случай **полной потери юрисдикции**
  (оба региона одновременно - катастрофа) остаётся восстановление из копий: потеря данных
  <= 15 мин, простой - часы (см. ADR-004).
- При полной потере юрисдикции её пользователи временно обслуживаются из соседних регионов
  в ограниченном режиме (публичные и некритичные операции) **без доступа к своим персональным
  данным** до восстановления.
- **Шина событий**: бизнес-топики зеркалируются односторонне из primary в standby (MirrorMaker 2,
  `IdentityReplicationPolicy`, sync offsets), поэтому второй регион видит те же события. RPO
  ограничена задержкой зеркалирования (секунды): неопубликованные события - в outbox, уже
  опубликованные - в зеркале (см. ADR-004).

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Репликация по классам данных (выбрано) | соблюдает локальное хранение, достаточно для аналитики | сложнее маршрутизация данных | Принято |
| Полная репликация всех данных во все регионы | простое чтение из любого региона | нарушает локальное хранение, дорого, конфликты | Отклонено |
| Единая общая база для всех регионов | единое состояние | задержка, единая точка отказа, нарушение локальных требований | Отклонено |
| Реплики только для чтения в каждом регионе | низкая задержка чтения | не решает задачу записи | Частично (для справочных данных) |

## Недостатки, ограничения и риски

- **Задержка репликации** справочных данных и агрегатов; митигируется асинхронной моделью и
  кэшированием на чтение.
- **Стоимость хранения** (данные живут в каждом регионе отдельно) - учитывается в FinOps.
- **Ограниченный глобальный обзор**: единой картины по персональным данным нет; для аналитики
  используются только обезличенные агрегаты.
- **Восстановление после отказа региона** для персональных данных идёт из локальных реплик
  и резервных копий в той же стране; целевые значения для этого сценария отличаются от штатных
  (см. ADR-004), нужны регулярные проверки восстановления.

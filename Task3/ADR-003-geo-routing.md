# ADR-003 (Task3). Механизм геомаршрутизации пользователей

## Общая информация

1. **Родительский артефакт** - `ADR-001-region-selection.md`, `ADR-002-data-replication.md`,
   условие Задания 3 (геомаршрутизация).
2. **Артефакт** - [`GeoRouting.puml`](GeoRouting.puml) / `.png` (изменения красным).
3. **Автор ADR** - Анзор Березгов, архитектор.
4. **Статус** - Принят.

## Контекст

Пользователи Юго-Восточной Азии и Южной Америки должны попадать в ближайший регион, чтобы
получить низкую задержку. Одновременно часть данных регулируется локально, поэтому не любой
пользователь может быть направлен в любой регион: для персональных данных нужен "домашний"
регион пользователя.

## Требования

| No. | Требование |
|---|---|
| 1 | Пользователь направляется в ближайший регион для низкой задержки. |
| 2 | Регулируемые данные обрабатываются в "домашнем" регионе пользователя. |
| 3 | При отказе региона трафик уходит в соседний здоровый регион. |
| 4 | Маршрутизация не требует изменений в клиентских приложениях. |
| 5 | Обновление маршрутов при отказе происходит автоматически. |

## Решение

### Слои маршрутизации

1. **Глобальный DNS с учётом географии и задержки** (geo-DNS).
   Отдаёт пользователю адрес ближайшего здорового региона по его географическому положению.
   Клиентское приложение не меняется - всё решается на уровне DNS.
2. **Проверки здоровья регионов.**
   Глобальный DNS знает состояние регионов; при отказе регион исключается из ответов,
   и трафик уходит в следующий ближайший.
3. **Определение домашнего региона.**
   Для регулируемых данных сервис определяет домашний регион пользователя (по стране профиля)
   и все операции с персональными данными выполняются там.
4. **Региональный периметр.**
   В каждом регионе трафик проходит через WAF, балансировщик и API Gateway/BFF (см. ADR-006),
   затем идёт в доменные сервисы региона.

### Правила маршрутизации

| Тип запроса | Куда направляется |
|---|---|
| Публичные операции (просмотр, расчёты без персональных данных) | ближайший здоровый регион |
| Операции с персональными данными (профиль, поездки, платежи) | домашний регион пользователя |
| Обезличенная аналитика | ближайший регион, агрегаты собираются централизованно |
| При отказе региона домашней юрисдикции | второй регион той же юрисдикции (персональные данные доступны); соседний регион другой страны - только для некритичных операций |

> Термин "домашний регион пользователя" здесь означает **активный регион его домашней
> юрисдикции**; при отказе этого региона запросы персональных данных переключаются на второй
> регион той же юрисдикции (см. ADR-002, ADR-004).

### Схема работы

```
Пользователь -> глобальный DNS (geo + задержка) -> ближайший здоровый вход
             -> WAF -> балансировщик -> API Gateway/BFF
             -> публичные операции: доменные сервисы этого региона
             -> операции с PII: проксирование в домашний регион (приватный канал)
```

### Согласованность домашнего региона

- Домашний регион определяется по стране пользователя и хранится в профиле (в самом регионе).
- Если пользователь путешествует, публичные операции идут в ближайший регион, а операции
  с персональными данными - по правилам домашнего региона.

### Как запрос с персональными данными попадает в домашний регион

Клиент не знает о регионах - всю логику принимает сторона сервиса:

1. geo-DNS отдаёт ближайший **здоровый вход**; публичные операции обслуживаются там же.
2. После аутентификации региональный API Gateway/BFF определяет **домашний регион**
   по токену/профилю пользователя.
3. Если домашний регион совпадает с регионом входа - запрос обслуживается локально. Если
   не совпадает (пользователь в поездке), PII-запрос **проксируется в домашний регион**
   по приватному межрегиональному каналу (mTLS); клиентский код при этом не меняется.
4. Для уже известного пользователя geo-DNS может сразу отдавать вход домашнего региона,
   но решение на стороне сервиса остаётся источником правды.

Компромисс: межрегиональный прокси-вызов добавляет задержку (один переход) и применяется
только к операциям с PII; публичные и аналитические запросы остаются в ближайшем регионе.
"Ручной выбор региона" в клиенте не требуется: домашний регион хранится в профиле и при
ошибке GeoIP задаётся привязкой (оператором), а не выбором в приложении.

## Альтернативы

| Альтернатива | Преимущества | Недостатки | Вердикт |
|---|---|---|---|
| Геомаршрутизация на уровне DNS (выбрано) | клиент не меняется, простота, низкая задержка | задержка обновления при отказе, кэш DNS | Принято |
| Выбор региона на стороне клиента | точный контроль | требует изменений в приложениях, логика в каждом клиенте | Отклонено |
| Единая глобальная точка входа | простота маршрутизации | все едут через один узел, растёт задержка | Отклонено |
| Один балансировщик на макрорегион | меньше компонентов | хуже задержка и изоляция | Отклонено |

## Недостатки, ограничения и риски

- **Кэширование DNS**: клиенты и провайдеры могут держать старый адрес; митигируется коротким
  временем жизни записей и проверками здоровья.
- **Задержка переключения** при отказе региона - от десятков секунд до минут; для критичных
  операций нужны ретраи на клиенте и идемпотентность на сервере.
- **Ложное определение региона**: по GeoIP пользователь может быть определён неверно;
  домашний регион хранится в профиле и при необходимости задаётся привязкой (не выбором
  в клиенте); серверное решение имеет приоритет над GeoIP.
- **Регулируемые данные** нельзя обслужить из чужого региона, поэтому при отказе региона
  персональные операции обслуживает второй регион **той же юрисдикции**; соседний регион другой
  страны используется только для публичных и некритичных операций. Полная потеря юрисдикции -
  осознанное ограничение комплаенса.
